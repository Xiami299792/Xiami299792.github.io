本章要解决的问题：前面五章讲的都是零件。这一章是组装——你会做出一个真正能用的东西。

具体做出来的是这样一个东西：

- 一个可以导入题库的刷题程序。
- 有答题界面，能看对错、能看进度。
- 有成绩记录和排行榜。
- 打包成一个文件，双击就能运行，同学不需要装任何东西。
- 同学和你连同一个 WiFi，就能用手机或电脑打开它刷题。
- 还能把它放到网上，拿到一个可以发给同学的网址。

可以先去玩一下成品。 下面这个地址是照本章的流程做出来的真实项目：

```text
https://junshililun-tfy.netlify.app/
```

打开之后你会看到「军事理论 · 刷题」的界面和题目数，可以直接刷题。

顺手做个实验： 在这个网址后面加上 `/api/board` 再访问一次，你会看到一个「页面不存在」的结果。

先不要急着下结论。 这个 404 有两种完全相反的解释：

- 「这个网站的服务器坏了」
- 「这个页面根本不需要服务器」

哪一种是真相？怎么判断？把这个实验留在心里，到 6.8 节我们会用它讲一件很重要的事：同一个现象可以推出完全相反的结论，而错误的那个往往听起来更合理。

你全程不需要会写代码。 你要做的是把话说清楚、在关键处做判断、验收结果。写代码是 AI 的事。

这一章会反复引用前面的章节。每一步开头都会写明用的是哪一章的知识——所以这一章同时是复习。

## 6.1 开始之前

### 6.1.1 你会用到前面的哪些东西

先看一张总表。哪一步卡住了，就回到对应的那一章。

| 这一步 | 用到哪一章的知识 |
|---|---|
| 把题库 PDF 变成数据 | 6.2.2（先报告结构）、第 1 章（Agent 会分多步执行） |
| 做出刷题页面 | 6.3.2（先追问）、第 5 章（用评审团审题面和文案） |
| 加上账号和排行榜 | 第 3 章（权限与工作区）、7.2.3（换阶段开新会话） |
| 让同学在同一 WiFi 上用 | 第 3 章（把端口开放出去的边界和审批） |
| 打包成一个文件 | 7.1.2（求助模板） |
| 写一份交付说明 | 第 5 章（用评审团审说明书）、第 3 章（脱敏） |
| 把它放到网上 | 7.1.2（报错求助）、5.8（单人反向复核） |
| 复盘 | 7.8.3（环境档案）、第 4 章（把做法回写成技能） |

### 6.1.2 准备三样东西

1. 一份题库文件。 最好是 PDF，里面有题目和答案。你手上有什么就用什么——四六级单词、专业课选择题、驾照题库都可以。如果实在没有，让它生成 50 道示例题凑数也行，不影响你走完整流程。
2. 一个专用的工作文件夹。 按第 3.3 节的规矩：新建一个，比如 `quiz-app`（用英文名，路径里的中文容易引起编码问题）。不要选桌面，不要选 C 盘根目录，不要放重要文件。
3. 半小时到两小时的空闲时间。 中间会被打断几次（审批弹窗、报错处理），别在地铁上做。

### 6.1.3 两个提醒

第一，这一章会用到网络共享。 到第 6.5 节，你要把你电脑上的一个端口开放给同一个 WiFi 里的人。这在宿舍里没问题，但在咖啡厅、图书馆这类公共 WiFi 里不要做。第 6.5 节会详细说。

第二，全程的产出都要存成文件。 第 7.2.7 节说过那条硬纪律：重要的东西不要只留在对话里。这一章每一步结束都会提醒你存文件。

准备好了就开始。

## 6.2 第一步：把题库变成数据

目标： 把一份 PDF 题库，变成一份结构化的数据文件。程序能读的那种。

用到： 第 7 章（让它先报告结构）、第 1 章（Agent 分多步执行）。

### 6.2.1 为什么要先做这一步

现在你的题库是给人看的——一份 PDF，题目、选项、答案混在一起。程序看不懂这种格式，它需要的是清清楚楚的数据：第几题、题干是什么、有几个选项、正确答案是哪一个。

这一步就是把「给人看的」变成「给程序看的」。这是所有这类项目的起点。

### 6.2.2 关键做法：先让它报告结构，别让它直接开工

这是第 7.4 节那句话的第一次实战。不要直接说「把这个 PDF 转成 JSON」——它会自己猜一套字段名，猜出来的未必合适，而且它不会告诉你它猜了什么。

要这样发指令：

我的工作区里有一份题库 PDF。请先读它，然后不要动手转换，只回答四个问题：

1. 它一共有多少道题？
2. 有哪几种题型（单选、多选、判断、填空）？各多少道？
3. 你打算用什么字段来存每一道题？给出字段名和含义。
4. 转换成结构化数据时，你预计哪些地方容易出错？

第 4 个问题特别有价值。让它自己提前说出风险点，你就能在它动手之前把要求定清楚。常见回答会是「选项里可能有换行」「多选题的答案可能识别不全」「题号可能混进题干」——这些你都可以提前约定处理方式。

### 6.2.3 它报告之后，你确认字段

一个够用的题库数据结构长这样：

```text
{
  "name": "题库名称",
  "v": 1,
  "questions": [
    {
      "id": "s001",
      "type": "single",
      "stem": "题干文字",
      "options": ["选项A", "选项B", "选项C", "选项D"],
      "answer": [0]
    }
  ]
}
```

五层信息，认识一下：

| 字段 | 含义 | 注意 |
|---|---|---|
| id | 每道题的唯一编号 | 不要重复，后面记录对错要靠它 |
| type | 题型 | 至少区分单选和多选 |
| stem | 题干 | 纯文字，不要带题号 |
| options | 选项数组 | 按顺序放，不要自己重排 |
| answer | 正确答案 | 用数组存，即使只有一项。单选是 [0]，多选是 [0,2] |

最后一条要单独说：答案用数组（带方括号）而不是直接写数字。 这样单选和多选就是同一套结构，程序不用为两种题型写两套逻辑。

确认的时候可以这样说：

字段这样定：id、type、stem、options、answer。answer 统一用数组，

单选也是数组。按这个结构生成，写到 `题库.json`。

### 6.2.4 生成之后必须做交叉检查

这一步不能省。它生成的数据一定会有错，不是它不用心，是 PDF 转文字本身就会出错。

做法是让它抽样核对：

从生成的题库里随机抽 10 道题，把 PDF 里的原文和你生成的数据并排贴出来，

逐字比对一遍，告诉我有没有不一致的地方。

为什么要随机抽而不是全查：全查太慢，而且它自己检查自己容易「看着像对的就过了」。随机抽 10 道，你亲自看一遍，如果 10 道里有 2 道有问题，说明整体错误率大约 20%，那就得整个重做或者换方法。

抽样还有一个好处：你自己也顺便检查了它的判断是否可靠。 如果抽出来的都没错，你就对这份数据有了基本的信任。

如果发现成批的错误（比如所有多选题答案都缺了一项），不要让它一条条改，直接说：

多选题的答案普遍不完整，请重新处理全部多选题，

处理完之后单独列出所有多选题的答案给我核对。

### 6.2.5 存文件

做完这一步，确认文件已经在工作区里了。跟它说：

确认 `题库.json` 已经保存在工作区，告诉我它的完整路径和大小。

从这一步开始养成的习惯：每完成一个阶段，就确认产出已经落成文件。 第 7.2 节那条纪律，在这里正式开始用。

这一步的验收：工作区里有一个 `题库.json`，你随机抽查过 10 道题，内容和原 PDF 一致。

## 6.3 第二步：做出刷题页面

目标： 一个网页文件，双击用浏览器打开就能刷题。

用到： 第 7 章（让它先追问）、第 5 章（评审团）。

### 6.3.1 为什么先做页面，不先做账号

因为先做能看见的东西，你能更快判断方向对不对。

如果先做账号系统，做完要等页面也做出来才知道好不好用；先做页面，半小时就能看到成果，不对可以立刻调。做东西的一个通用原则：先做能最快看到结果的那部分。

### 6.3.2 让它先追问

第二个实战。这次要说的是：

我要做一个刷题页面，单个 HTML 文件，双击就能在浏览器里打开做题。

题库用工作区里的 `题库.json`。

先别动手。先问我最多 5 个问题，把需求问清楚，再给我方案，我确认后你再做。

它会问的问题大概是这样，你可以照着准备答案：

- 要不要乱序出题？（建议：要，否则每次顺序一样，会背答案）
- 答错了要不要能重做？
- 要不要计时？
- 手机上要不要能正常看？（建议：要，同学多半用手机）
- 要不要显示答案解析？（题库里如果没有解析字段，就显示正确答案）

准备答案的过程，其实就是你理清需求的过程。 这也是第 7 章说的：写不清楚往往是因为还没想清楚——它一追问，你就被迫想清楚了。

### 6.3.3 你的指令可以这样写

它问完之后，你这样回：

按这样定：

1. 每次开始随机打乱题目顺序，选项顺序也打乱。
2. 答完一题立刻显示对错，错了显示正确答案。
3. 答错的题在最后重做一遍。
4. 不做计时。
5. 手机和电脑都要能正常显示。

做成单个 HTML 文件，所有代码写在文件里，不要引用外部文件。

文件名 `刷题.html`，存到工作区。

「做成单个 HTML 文件、不要引用外部文件」这句话很重要。 如果你的页面引用了外部的样式文件或脚本文件，就得带着一堆文件一起发，同学少拷一个就打不开。单文件是这里最省事的选择。

### 6.3.4 用评审团审一次（第 5 章的实战）

页面做出来之后，先别急着往下走。用第 5 章的方法审一次。

不过这次不需要三个角色，用单人反向复核就够了（第 5.8 节）：

开一个新的会话，把 `刷题.html` 给它，说：

你的唯一任务是找出这个页面的问题。从「一个第一次用的人会不会懵」

的角度找。只写问题，不要写优点，至少找出五个。

重点检查三类问题：

1. 题目之外的文字。 按钮上写「提交」还是「下一题」？答错之后的提示是「错误」还是「正确答案是 B」？这些字眼直接决定同学用起来顺不顺。
2. 出错时怎么办。 题库文件读不到时会怎样？是一句看不懂的报错，还是「没找到题库文件，请检查」？
3. 边界情况。 题库只有一道题时正常吗？题目选项只有两个时正常吗？

审完改一轮。这一步花二十分钟，能省掉同学二十条「这个怎么用」的消息。

这一步的验收：双击 `刷题.html`，能正常答题、能看到对错、手机打开也能用。

## 6.4 第三步：加上账号、成绩和排行榜

先决定走哪条路，再动手。

这一步只有做「联网版」时才需要——就是同学各自注册、成绩传到你这里、能看到全班排行榜，这些都要服务端。如果你只是想让大家能刷题，整段跳过这一步（6.5、6.6 也一起跳过），直接做 6.8.3 的做法一（静态托管）。

|  | 纯前端路线（建议先做） | 联网版路线 |
|---|---|---|
| 走哪几步 | 6.2 → 6.3 → 6.8 → 6.7 | 6.2 → 6.3 → 6.4 → 6.5 → 6.6 → 6.8 → 6.7 |
| 同学怎么用 | 打开网址就能刷 | 要你的电脑开着 |
| 有账号和排行榜吗 | 没有，记录存在各自手机上 | 有 |
| 好做吗 | 一两小时 | 麻烦得多，失败面也大 |

为什么要你先看这张表？ 因为这个项目真实做出来之后，作者才发现：他花大力气写的账号、排行榜和管理后台，学生端页面一次都没调用过——那是永远不会有数据的死代码（完整经过见 6.8.7）。先知道有这个坑，你就不会白做一遍。

目标： 同学各自注册账号，成绩被记录下来，能看到排行榜。

用到： 第 3 章（权限与工作区）、第 7 章（换阶段开新会话）。

### 6.4.1 开一个新会话（第 7 章的实战）

这一步开始之前，先开一个新会话。

理由在第 7.2 节讲过：到目前为止，会话里装的全是「怎么把 PDF 转 JSON」「怎么调整页面样式」的内容。现在要做的是完全不同的事——服务端、账号、数据存储。旧内容只会干扰它。

但开新会话意味着它什么都不知道了。所以你要给它交接：

我要给现有的刷题程序加账号功能。先看一下工作区里的 `题库.json` 和

`刷题.html`，了解一下现在做到哪了。

这就是第 7.2.7 节说的：文件是你跨会话的传递方式。 因为前面每一步都存了文件，这里才能顺利交接。

### 6.4.2 这一步和前面不一样

前三步，它动的是你的文件。这一步开始，它会开一个服务，让别人的电脑能连上你的电脑。

这是性质上的变化。所以：

- 权限要重新看一遍。 按第 3.4 节，确认你现在还是「工作区可写」，没有为了省事改成「完全访问」。
- 每一步都看它的计划再批准。 这一阶段的操作影响更大，审批弹窗要认真读。

### 6.4.3 让它先列方案

第三个实战，也是最需要看方案的一步：

我要给刷题程序加账号功能。先别动手，先告诉我你的方案：

1. 你打算建哪些文件？每个文件负责什么？
2. 账号和成绩存在哪里？用什么格式存？
3. 同学的密码怎么处理？会不会用明文存？
4. 别人怎么登录、怎么区分是谁在做题？
5. 需要我做什么决定？

第 3 个问题必问。 如果它说「明文存密码」，你要明确要求改成加密存储。这不是过度谨慎——这个程序要在同学之间用，哪怕只是练习项目，也不该让别人的密码以明文躺在一个文本文件里。

第 5 个问题也很重要。它可能会问你：要不要设管理员账号？一个人能不能重复注册？成绩按最高分还是最近一次？这些是产品决定，只有你能做。

### 6.4.4 一个够用的方案长什么样

它给出的方案大概包含这几块：

| 部分 | 作用 |
|---|---|
| 服务端程序 | 接收请求、判断对错、记录成绩 |
| 页面文件 | 登录页、刷题页、排行榜页 |
| 数据文件 | 存账号和成绩 |
| 管理入口 | 你能看到所有人的数据，能删掉乱注册的账号 |

关于数据文件，有一件事必须知道并且记住：

所有数据都在一个文件里。备份就是复制这一个文件。换电脑就是把程序和这个文件一起拷走。

你的程序可能很复杂，但你的数据极简单。 想备份的时候不用去翻一堆文件夹，复制那一个文件就行。

### 6.4.5 你自己也要试一遍

做完之后，不要只看它说「完成了」：它说完成不等于真完成。

你要亲自做四件事：

1. 注册一个新账号。
2. 完整做一轮题。
3. 退出，用同一个账号重新登录，看成绩还在不在。
4. 打开排行榜，看你刚才的成绩有没有出现。

第 3 步最容易出问题。 很多初版程序刷完分能看到，一重新登录就没了——数据没真正存下来。

如果有问题，这时候用第 7.1 节的求助模板：

我在做什么：测试刷题程序的成绩保存

我执行的操作：注册账号、做完一轮题（10 题，对了 7 题）、退出登录、重新登录

我期望的结果：重新登录后能看到刚才 7 分的成绩

实际发生的结果：成绩显示为 0，排行榜里也没有我

完整报错：（如果终端或浏览器有报错，原文粘贴）

我已经试过：刷新页面，无效

这一步的验收：自己注册、刷题、退出、重新登录，成绩还在，排行榜能看到。

## 6.5 第四步：让同学用上

目标： 同学连同一个 WiFi，就能打开你的刷题程序。

用到： 第 3 章（权限边界与审批）。

### 6.5.1 这一步在做什么

到目前为止，程序只有你自己能访问。这一步是让同一个网络里的其他人也能访问。

做法是：程序启动后会在你的电脑上开一个「端口」，同一个 WiFi 里的其他设备可以通过你的电脑地址加端口号访问它。

你的程序启动时会在窗口里打印出一行地址，形如：

```text
同一 WiFi 下的同学可以访问：http://192.168.x.x:8080/
```

这行地址就是要发给同学的东西。

### 6.5.2 三个前提，缺一不可

同学能不能打开，取决于三件事：

1. 同学和你连的是同一个 WiFi。 不同网络之间访问不了，这是网络本身的限制，不是程序的问题。
2. 你的电脑防火墙允许了。 第一次运行时 Windows 会弹窗问你「是否允许此应用通过防火墙」，必须点「允许」。
3. 你的电脑不能关机、不能睡眠。 你的电脑就是服务器，它睡了所有人都打不开。

第 3 条需要提前跟同学说清楚。否则会出现「上午能用下午打不开」的困惑——其实是你电脑休眠了。

### 6.5.3 安全边界（这一节不能跳过）

这一步的本质是：你把自己电脑上的一个端口开放给了同一个网络里的人。

所以有三条纪律：

第一，只在可信的网络里做。 宿舍 WiFi、家里的 WiFi 可以。咖啡厅、图书馆、火车站这类公共 WiFi 不要做——同一个网络里可能有陌生人。

第二，只开放这个程序用的端口，不要动防火墙的其他设置。 你要做的只是在弹窗里点一次「允许」。不要为了图省事把防火墙整个关掉。

第三，用完就关。 不刷题的时候把你那个程序的窗口关掉，端口就关了。不需要一直开着。

还有一件事：不要让同学访问到你的管理入口。 管理入口是给你自己用的（看数据、删账号）。如果把地址发出去的时候把管理入口也带上了，同学可能误进去乱改数据。

如果你不确定程序是怎么处理的，直接问你自己的 AI：

我这个刷题程序有两个入口：刷题页和管理后台。我要把刷题页发给同学，

怎么保证他们访问不到管理后台？

### 6.5.4 端口被占用怎么办

有时程序启动会说端口被占用。换一个端口重新启动就行——端口是多少由程序自己定，看窗口里打印的那一行。换不了就先关掉占用这个端口的程序。

关于端口，一个有用的常识：它就像门牌号。 「端口被占用」的意思是那个门牌号已经被别的程序用了，换个号就行。这不是错误，是正常情况。

这一步的验收：用你自己的手机（连同一个 WiFi）打开那个地址，能正常刷题。这一步一定要用另一台设备测，用你自己的电脑测不算——那走的是本机访问，不经过网络。

## 6.6 第五步：打包成一个文件

目标： 把程序打包成一个 exe 文件，双击就能运行。同学不用装任何东西，不用敲命令。

用到： 第 7 章（求助模板）。

### 6.6.1 为什么要打包

现在的程序要运行，得在你的电脑上敲命令启动。发给同学，他做不到。

打包之后，你的程序和一个运行时被合成了一个文件。双击它，程序就跑起来了，不需要预先装任何东西。

原理三句话：

1. 正常情况下，程序需要先装一个运行环境（这里指 Node）才能跑。
2. 打包工具把这个运行环境和你的程序合成一个文件。
3. 顺便把你的网页文件也塞进去，这样就不需要额外带一堆文件。

### 6.6.2 让它写打包脚本

你这样发指令：

请写一个打包脚本，把服务端和页面打包成一个单文件的 Windows exe。

要求：

1. 双击就能运行，自动打开浏览器。
2. 不需要预先安装 Node。
3. 打包完告诉我怎么验证它真的能跑。

它会生成一个脚本（比如 `build-exe.js`）。让 DSH 去运行它，不要自己在系统的 PowerShell 里敲 `node build-exe.js`——桌面版自带的运行环境不在系统 PATH 里，你会撞上「`node` 不是内部或外部命令」。直接说：

请运行这个打包脚本，把结果告诉我。

### 6.6.3 三个真实报错（本章最有价值的一段）

打包这一步大概率会出错。不要慌——这正是第 7 章教的东西派上用场的地方。

下面三个报错都是真实出现过的。重点不是记住解决方案，而是看怎么把报错交给 AI。

### 报错一：EPERM

现象： 打包跑到一半停住，报错里有 `EPERM` 这个词。

含义： `EPERM` 是「操作不被允许」。EPERM 表示这次调用被系统拒绝了。常见原因有两种：一是 Windows 上不经命令解释器直接启动 .cmd 结尾的程序（下面这个例子就是）；二是权限不足或被杀软拦住。先看报错里被拒绝的到底是哪个程序、哪一步。不要先用「以管理员身份运行」去试，它解决不了这一类问题。

怎么交给 AI：

我在做什么：运行打包脚本 `node build-exe.js`，把程序打包成 exe

我期望的结果：生成 exe 文件

实际发生的结果：跑到调用打包工具的步骤就停了

完整报错：

```text
Error: spawnSync npx.cmd EPERM
at ...
```

我已经试过：以管理员身份重新运行，还是同样报错

关键在最后一段：把 `EPERM` 那行原文贴上，再说清是「哪一步」出的错。 只说「打包失败了」几乎得不到有用的回答。

结论（供你对照）： 解决办法是让这个调用经过 shell（命令解释器）。也就是在调用参数里加上 `shell: true`。程序里对 Windows 的 `.cmd` 程序需要这一步特殊处理。

### 报错二：判断「是否被打包」的逻辑错了

现象： exe 生成成功，但双击运行的行为不对——它以为自己还是普通脚本，去磁盘上找那些已经被内嵌进去的文件，然后找不到。

原因： 打包后的程序和普通的 Node 程序，需要用不同方式读取内嵌资源。判断「我现在是不是被打包的那个版本」，代码里可能写成了「检查某个模块存不存在」。

问题在于：这个模块在打包后依然存在。 所以这个判断永远返回「是」，逻辑就错了。

正确做法是调用该模块提供的判断函数，而不是判断模块本身在不在。

怎么交给 AI：

打包后的 exe 双击能启动，但它去磁盘上找 `public` 目录里的文件，

找不到就报错了。这些文件应该已经内嵌进去了。

我怀疑是判断「当前是不是打包版本」的写法有问题。

现在代码里写的是判断 `node:sea` 这个模块是否存在，这样对吗？

注意这段提问的方式： 描述现象 + 说出自己的怀疑 + 提出一个具体问题。这比「打包装好后运行不了，怎么办」有效得多。

### 报错三：找不到替换标记，打包中断

现象： 脚本跑到一半自己退出了，提示找不到某个标记。

原因： 这类打包脚本的工作方式是「在源文件里找一个占位行，把它换成真正的数据」。如果源文件被改动过，占位行变了或者没了，脚本就找不到目标，于是主动退出。

这其实是好事。 脚本主动报错退出，比它找不到目标还硬着头皮往下跑要好得多——后者会生成一个看起来正常、实际上有问题的文件。

怎么处理：

打包脚本报错说找不到 `const EMBEDDED = null;` 这一行。

请检查一下现在源文件里这一行是不是被改过，应该怎么改脚本或源文件。

### 6.6.4 从这三个报错里能学到什么

回头看，三个报错的共同点是：

1. 报错信息里都有关键词。 `EPERM`、模块名、那一行代码——这些词就是线索。
2. 都要说清「我在做什么」。 同一个报错在不同阶段出现，原因不同。
3. 交给 AI 的时候，原文比你自己的理解更值钱。

第 7.1 节的模板在这里完整地用了三次。

这一步的验收：得到一个 exe 文件，双击能运行，窗口出现，浏览器自动打开并且能刷题。

## 6.7 第六步：写一份给同学的说明

目标： 一份说明书，让完全不懂电脑的同学也能用起来。

用到： 第 5 章（评审团）、第 3 章（脱敏）。

### 6.7.1 为什么必须写

程序做出来了，但同学不知道：

- 双击之后弹出的黑色窗口是什么，能不能关？
- 那个地址打不开是为什么？
- 默认的管理员账号密码是多少，要不要改？

没有说明书的程序，等于没做完。 而且你会在群里被反复问同样的问题。

### 6.7.2 说明书必须包含的七件事

先看你走的是哪条路线（6.4 节开头那张表）。说明里只能写你真正做出来的东西——6.8.7 节那个真实案例，栽的就是说明书写了页面上根本不存在的东西。

| 内容 | 为什么要写 | 哪条路线要写 |
|---|---|---|
| 怎么启动 | 双击哪个文件、或者打开哪个网址，之后会发生什么 | 两条都要 |
| 两个地址分别是什么 | 哪个是刷题页（发给同学）、哪个是管理入口（只给自己） | 联网版 |
| 那个黑色窗口是什么 | 说清「关掉它 = 停止服务」，避免同学误关 | 联网版（打包成 exe 之后） |
| 默认管理员账号，以及立刻改密码 | 默认密码是公开的，不改等于没锁门 | 联网版 |
| 同学怎么访问 | 需要同一个 WiFi，地址从哪来 | 看你的部署方式（6.8 节） |
| 端口被占用怎么办 | 说明会自动换端口，看窗口里打印的 | 联网版 |
| 数据在哪、怎么备份 | 复制那一个文件就是备份 | 联网版 |

走纯前端路线的话，说明书写清三件事就行： 网址是什么、手机上怎么打开、成绩存在哪里——它存在同学自己的手机里，换个手机或者清掉浏览器数据就没了。这一点必须写，否则同学会以为成绩是存在你这里的。

### 6.7.3 写说明书的指令

请为这个刷题程序写一份使用说明，文件名 `使用说明.txt`。

读者是完全不懂电脑的同学，所以要：

1. 用短句，不用术语。必须出现术语时，用一句话解释。
2. 把「怎么启动」放在最前面。
3. 说明那个黑色窗口是什么，什么时候可以关、什么时候不能关。
4. 单独用一段提醒管理员立刻改掉默认密码。
5. 说明数据存在哪个文件、怎么备份。
6. 不要写任何我个人的路径、密钥或账号信息。

上面第 3、4、5 条只对联网版成立。 走纯前端路线的话，把这几条删掉，换成 6.7.2 末尾那三件事——不要让说明书承诺页面上没有的东西。

第 6 条不能省，原因见下一节。

### 6.7.4 脱敏：这一步最容易出事

说明书是要发给别人的，所以它里面的每一个字都会被人看到。

发出去之前，检查四件事：

1. 有没有你的用户名和完整路径。 比如 `C:\Users\你的真名\...`。
2. 有没有你的 Key。 搜一下「key」「密钥」「token」，看到就删。
3. 默认密码有没有提醒改。 不提醒，同学就会一直用默认的。
4. 有没有不该公开的信息。 学号、手机号、群里的通知截图。

一个真实的教训： 这类说明书里最容易留下的就是默认管理员密码。你在写的时候觉得「反正只有我们宿舍用」，但这份文件会被转发，会留在别人的电脑上，可能过一年还在。默认密码必须在说明书里明确要求修改，而你自己那份也不能一直用默认值。

### 6.7.5 用评审团审一次（第 5 章的第二次实战）

说明书的目标读者是「不懂电脑的同学」，所以使用方代表这个角色特别有用。

用单人反向复核就行：

你要扮演一个完全不懂电脑的大一新生。读这份使用说明，只回答两个问题：

1. 哪些地方你看不懂？逐条列出。
2. 照着它做，你能成功打开刷题页吗？如果哪一步会卡住，说明卡在哪。

第 2 个问题是关键。 它逼对方真的「照着做一遍」，而不是泛泛地说「写得还行」。

这一步的验收：把 exe 和说明书放进一个文件夹，发给一个同学，他能自己用起来，没有来问你。

## 6.8 第七步：把它放到网上

目标： 给同学一个网址，不连你的 WiFi 也能打开。

用到： 第 3 章（脱敏）、第 7 章（报错求助）、第 5 章（用评审团审说明书）。

### 6.8.1 两个方向相反的坑

动手之前必须先想清楚一件事：你做出来的东西，是「纯前端」还是「需要服务端」？

这两种东西的部署方式完全不同，选错了会出现两种失败——而且它们长得很像，处理方式却相反：

坑一：你的东西需要服务端，却只做了静态托管。

静态托管（Netlify 这类）只放文件，不跑程序。页面能打开，但页面要调用的那些接口不存在，注册、登录、成绩、排行榜会静默失效——不报错，只是用不了。

坑二：你以为它需要服务端，其实它根本不需要。

这种情况下静态托管就是最合适的方案。你反而可能去做一堆没必要的复杂配置（自己电脑常开、内网穿透、跳转……），把简单的事做复杂了。

所以第一步不是挑方案，是搞清楚你的项目到底是哪一种。

### 6.8.2 第一步：判断你的项目是哪一种

有一个很快的判断办法：看你的页面有没有向服务器要数据。

在你的页面文件里搜索这几个词：

| 搜什么 | 搜到了说明什么 |
|---|---|
| fetch( | 页面在向服务器要数据 |
| XMLHttpRequest | 同上（老写法） |
| localStorage | 数据存在浏览器本地，不需要服务器 |
| 注册、登录、排行榜 | 有这类功能，通常需要服务器 |

判断规则（这是缩小范围的粗略办法，不是结论）：

- 搜到 `fetch` 或 `XMLHttpRequest`，而且请求的是你自己的接口 → 大概率需要服务端，按 6.8.4 的做法二准备。
- 只搜到 `localStorage`、没搜到网络请求 → 大概率是纯前端，可以先按 6.8.3 的做法一部署。

为什么只能算「大概率」： 这几个词可能出现在注释、字符串或者引用的第三方文件里，搜到不等于真的在用；反过来，页面也可能用别的方式发请求（比如引用了别人打包好的库），搜不到不等于没有。

决定性的验证只有一次：部署完打开那个地址，看它到底能不能用（6.8.3 第 5 步、6.8.6 的清单）。搜索结果只用来决定先试哪条路。

自己看不出来，就直接问它：

```text
请检查工作区里的页面文件（第 6.3 节让你建的那个 `刷题.html`），回答两个问题：
一、这个页面有没有向后端发请求？如果有，请求的是哪些接口？
二、如果没有后端，它的数据存在哪里？
请引用具体代码位置。
```

这个检查要养成习惯。 因为「写了」和「用上了」是两件事：服务端可能确实有接口，但页面从来没调用过它们——那这些功能对使用者来说就等于不存在。6.8.7 节有一个真实案例，作者就是在这里判断错的。

### 6.8.3 做法一：静态托管（适合纯前端）

适合「我只想让同学有个地方打开就能刷题」这种情况。

1. 把页面文件单独放进一个文件夹：纯前端路线就是第 6.3 节那个 `刷题.html`；联网版项目里通常在 `public/` 目录下，叫 `index.html`。
2. 打开 Netlify 的拖拽部署页面（搜索「Netlify Drop」）。
3. 把这个文件夹整个拖进去。
4. 等上传完成，它会给你一个随机地址，形如 `random-name-12345.netlify.app`。
5. 想换成好记的：进 Netlify 控制台 → 这个站点 → Site configuration → Change site name。

你应该看到：地址能打开，页面显示出来。

然后必须做一件事：验证接口。 在这个地址后面加上 `/api/board`，访问一下：

- 返回一堆数据 → 你这次部署真的有后端，很好。
- 返回 404，或者一个「页面不存在」的页面 → 这次部署里没有后端，账号和排行榜在这个网址上用不了。

这一步不能省。页面能打开，不代表功能能用。

注意这个 404 能说明什么、不能说明什么。 它说明的是你这次部署的方式没有后端；它不能说明你的源码里没有这些接口。这两件事很容易混，6.8.7 节那个真实案例就栽在这里——服务端接口明明存在，只是页面从没调用过，而作者拿这个 404 去证明「接口不存在」，结论正好反了。

### 6.8.4 做法二：让网址跳到你的电脑

如果你想让同学用一个好记的网址，而实际访问的还是你电脑上跑着的程序（这样账号和排行榜可用），可以用跳转。

道理是：跳转发生在同学的浏览器里，不在服务器上。

- 同学的手机在校园网内 → 打开网址 → 浏览器收到「去这个地址」的指令 → 直接访问你电脑的局域网地址。这条路是通的。
- 如果改成「反向代理」（让托管服务器替你去取内容），行不通——你的电脑是校园内网地址，外面的服务器根本路由不到它。

做法：

1. 新建一个文件夹，里面放一个 `_redirects` 文件，内容是一行：

```text
/*    http://你的局域网IP:端口/:splat    302!
```

把 IP 和端口换成程序窗口里打印的那个。结尾那个 `!` 不能省——它表示「这条规则优先于同名文件」。少了它，第 2 步放的 `index.html` 会顶掉这条规则，别人打开网址看到的是那个占位页，而不是跳转。

2. 再放一个 index.html 当占位页——万一条跳转失效，打开网址的人能看到一个手动链接兜底。
3. 把整个文件夹拖到 Netlify Drop。

状态码写成 302，不要写 301。 301 会被浏览器永久记住，配置写错了改完也不生效，很难调试。确认一切正常之后，再考虑换成 301。（不写状态码时 Netlify 默认给 301，所以这里必须显式写。）

这个文件会公开。 拖上去之后，任何人都能打开那个网页、看到里面写的地址。里面只有你的局域网地址（`192.168.x.x` 这类），外网访问不到它，所以风险有限。

但不要往里面写别的东西：公网 IP、路由器管理地址、密码、学号，一律不写。

### 6.8.5 三个会让你失败的前提

这三条作者都实测过。任何一条不成立，这个方案就走不通。

| 前提 | 怎么测 | 不成立怎么办 |
|---|---|---|
| 校园网允许设备互访 | 让同学连同一个 WiFi，手机直接打开 http://你的局域网IP:端口/ | 很多校园 WiFi 开了「客户端隔离」，同网设备互相访问不了。改用 6.8.3 的做法一（静态托管）：页面直接放到网上，谁都能打开，代价是没有后端，账号和排行榜用不了 |
| 你的 IP 不变 | 重启路由器之后看地址变没变 | 变了就得回来改 _redirects 重新传一次。这一点没法一劳永逸，接受它，或者改用做法一 |
| 托管站点本身访问稳定 | 用自己的手机流量打开一下那个网址 | 国内访问这类国外托管服务可能不稳。所以一定要同时把局域网地址发到群里，那才是最快最稳的入口 |

### 6.8.6 部署之后必须做的验证

不要只看页面能不能打开。 页面打开是最容易通过的一关，也是信息量最小的一关。

按这个清单逐条过：

1. 打开网址，看首屏。 页面出来了——这一关几乎总能过。
2. 翻出你的说明文档，把里面承诺的每一条功能列出来。
3. 逐条在线上点一遍。 说明里写「能注册」，你就去点注册；写「能看排行榜」，你就去看排行榜。
4. 对不上的地方，全部记下来。

第 2 步最容易被跳过，但它是最关键的一步。 因为「我以为它有什么功能」和「说明文档承诺了什么功能」经常不一致——而同学只会看说明。

一个残酷但常见的结论：

说明里承诺的功能，如果在页面上找不到入口，那它对同学来说就是不存在。

不管你的服务端代码写得多完整。

### 6.8.7 真实案例：同一个 404，两种解释

这一节讲一件真实发生的事。花两分钟读完，它演示了第 5 章那个评审团到底能防住什么。

背景： 这个刷题项目做完后，作者把页面部署到静态托管，拿到一个网址。和 6.1 节一样，访问网址后面的 `/api/board`，返回 404。

第一种解释——作者的判断（错的）：

「静态托管不跑程序，所以账号和排行榜在线上用不了，只有刷题能用。」

听起来完全合理，而且正好符合 6.8.1 说的「坑一」。作者据此在书里写下了「页面背后要调用的接口不存在」。

第二种解释——另一个评审员去数了一遍页面上的东西：

「这个页面里一个网络请求都没有。它的题库是内嵌的，数据存在浏览器本地。所以那个 404 不代表任何功能坏了——它只说明这个页面根本不需要后端。 刷题、错题本、统计在线上完全可用，线上网址反而是最好用的入口。」

谁对？ 打开 `index.html` 一查就知道：文件里搜不到任何 `fetch` 或 `XMLHttpRequest`，也没有「注册」「排行榜」这些字。

第二种解释是对的。作者判断错了。

错在哪里？ 他先入为主地按「一个正经的刷题网站应该有后端」去推断，然后拿一个 404 去印证自己的推断。这正是第 5.1 节讲的「替自己找理由」。

这个案例真正的发现，比原来那个结论重要得多：

- 服务端的注册、登录、排行榜接口和整个管理后台确实存在，代码写得也完整。
- 但学生用的那个页面从来没有调用过它们。
- 所以这些接口和管理后台属于永远不会有数据的死代码——后台打开会一直显示「没有用户」「还没有成绩」。如果去排查，会对着一堆 0 查很久。

这就是「写了」和「用上了」的差距。 功能不是写出来就算有，要有人能点到它才算有。

还有两件事是这个案例带来的：

- 给同学看的说明里写着「学生用这个地址注册、刷题、看排行榜」——承诺了两个页面上根本不存在的东西。
- 两份说明里，从头到尾都没有出现那个真正能用的线上网址。

一个人对着代码往下推断，另一个人去数页面上的标签和网络请求——两个视角一对照，错误就露出来了。你审自己永远发现不了这种错，因为你会顺着自己的推断一路走下去。

### 6.8.8 交付时给同学两个地址

这一步做完，你应该给同学两个地址，并且说清区别：

- 局域网地址（`http://192.168.x.x:端口/`）：最快最稳，但要求连同一个 WiFi，而且你的电脑得开着。
- 网上地址（`xxx.netlify.app`）：同学在任何地方都能打开这个网址，但能不能真正用，取决于你选了做法一还是做法二。

不要只给一个。 只给局域网地址，同学换个网络就打不开；只给网上地址，万一它只是个静态页面，同学会以为功能齐全，注册半天才发现成绩存不上。

这一步的验收：网址发给一个同学，他能打开；你按 6.8.6 的清单逐条验证过说明里承诺的功能；并且你能清楚说明哪个地址能干什么、不能干什么。

## 6.9 复盘：把它变成你自己的能力

东西做完了。最后这一步是很多人会跳过、但价值最高的一步。

用到： 第 7 章（环境档案）、第 4 章（回写成技能）。

### 6.9.1 让它评估这次的过程

在新会话里问它：

我们刚才一起做了一个刷题程序，从 PDF 题库做到打包成 exe。

请回答三个问题：

1. 整个过程里，哪一步花的时间最多？为什么？
2. 哪些地方你误解了我的意思？我当时应该怎么描述才能避免？
3. 如果再做一遍，你会建议调整哪一步的顺序？

第 2 个问题最有用。 它会告诉你你的描述在哪些地方有歧义——这些就是你下次要改进的表达方式。第 7.5 节说的「描述清楚比换模型划算」，改进的依据就在这里。

### 6.9.2 把可复用的部分写成技能（第 4 章的实战）

这次做的东西里，有哪些是你以后还会重复遇到的？

- 「把 PDF 资料转成结构化数据」——这个你以后一定会再用。
- 「把 Node 程序打包成单文件 exe」——做其他小工具也会用到。
- 「写一份给不懂电脑的人看的说明」——同样的需求会反复出现。

挑一个，让它回写成技能：

把「把 PDF 题库转成 JSON」这一步的做法写成一个技能，放到 `~/.dsh/skills/` 下。

要求：`description` 里写上我会说的那几句话；步骤写成可执行动作；

必须包含「抽样交叉检查」这一步；再加一节「如果做不到」。

写完按第 4.4 节的方法验证：用一个不提技能名字的新任务去试。

到这里你就有第一个真正属于自己的技能了——它不是抄来的，是你自己做出来的。

### 6.9.3 更新环境档案（第 7 章的实战）

往 `环境档案.md` 里补几行：

- 这次做的是什么、用了多长时间。
- 遇到了哪三个报错、分别怎么解决的。
- 装了哪些新东西。
- 新增了哪个技能。

为什么值得记： 三个月后你要再做类似的东西，这个文件能让你少走一大半弯路。第 7.8 节说过，它是「你的 DSH 和别人不一样」的地方——现在它真的不一样了。

### 6.9.4 关于「用它做作业」的一句话

这个刷题程序本身就是个例子：它是用来学习的东西，不是用来交差的东西。

用它刷题、用它整理资料、用它做练习题，这些是学习。让 AI 直接写出作业答案交上去，你得到的是一个分数，代价是你没学会。

一个简单的自检标准：你能不能把做出来的东西讲给同学听，让他也做出来？ 能讲清楚，说明这一章的内容你真的拿到了。

## 6.10 本章总验收

先确认你走的是哪条路线（第 6.4 节开头那张表）——两条路的验收不一样，不要拿另一条路的标准来要求自己。

走纯前端路线（6.2 → 6.3 → 6.8 → 6.7）的验收：

顺序说明： 先做 6.8 部署、再写 6.7 说明书。这样写说明书时，同学怎么访问、成绩存在哪里都已经确定了，不用回头改。

1. 一个能打开的网址。 发给一个同学，他用手机就能打开、能答题、答错了能看到正确答案。
2. 一份能直接发给同学的说明。 他自己能用起来，没有来问你。
3. 至少解决过一次真实报错。 用第 7.1 节的模板，把报错原文交给 AI，并且解决了它。两条路都会遇到报错：纯前端路线通常在 6.3（生成页面）和 6.8（部署）这两步，联网版还可能出现在 6.6（打包）。

走联网版路线（多做 6.4 → 6.5 → 6.6）的额外验收：

1. 一个能双击运行的 exe 文件。 双击它，窗口出现，浏览器自动打开。
2. 账号和成绩真的能存下来并看到。 自己注册一个账号、做一轮题、退出、重新登录，成绩还在；排行榜里能看到自己。

注意：这一条只对联网版成立。如果你做的是纯前端版，页面上没有注册和排行榜，成绩只存在同学自己的手机里——这是正常的，不是没做完。这一点在 6.8.7 节有完整解释。

验收：按你选的路线，完成上面 1–3 条；联网版再加「能双击运行的 exe」和「账号成绩存得住」两条。

## 6.11 做完之后

到这里，你已经把整套流程走完了一遍。回头看，你其实做了这几件事：

- 把权限收在了一个文件夹里，让它出不去（第 3 章）。
- 遇到报错没有慌，用模板把问题交给了 AI（第 7 章）。
- 让它先追问再动手，省掉了返工（第 7 章）。
- 把反复要做的事写成了技能（第 4 章）。
- 用评审团检查了自己的作品（第 5 章）。

附录里有命令速查卡、术语卡和模板，需要的时候翻一翻。
