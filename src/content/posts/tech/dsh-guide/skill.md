本章要解决的问题：如果你已经用过一阵子，一定会遇到这种情况——同一套要求，你已经解释过第三遍了。「要用中文」「不要用专业术语」「表格要有表头」「文件存到那个文件夹」……每次都重说一遍，累，而且它每次做得还不太一样。

技能就是解决这件事的。这一章讲清技能是什么、怎么写、怎么从 GitHub 上找别人写好的，以及怎么判断一个技能能不能装。

## 4.1 先决定：这件事需要写技能吗

不是所有事都值得写技能。写之前先用下面这张表判断。

| 你的情况 | 用什么 | 判断标准 |
|---|---|---|
| 这件事只做这一次 | 直接跟它说 | 一次性，不值得固化 |
| 这件事反复做，要求基本固定 | 写技能 | 你已经第三次解释同一件事了 |
| 这件事需要新能力、新界面、新接口 | 装插件 | 要动系统能力，不是靠说明能解决的 |

「你已经第三次解释同一件事了」就是写技能的信号。

分清两个容易混的东西：

- 插件是零件，装上之后 DSH 多了个功能或界面。
- 技能是说明书，告诉 AI 某类事情该一步步怎么做。

一个是能力，一个是方法。技能不能让 DSH 会做它本来不会做的事，它只是让它按你的方式做。

## 4.2 技能长什么样

一个技能就是一个文件夹，放在 `~/.dsh/skills/` 下面（Windows 上是 `C:\Users\你的用户名\.dsh\skills\`）。

打开它的最省事办法： 在文件资源管理器的地址栏（不是浏览器）里输入 `%USERPROFILE%\.dsh`，回车。

它就在你的用户文件夹里，名字以点开头。这个文件夹以后还会反复出现（放配置、放会话记录、放插件）。

文件夹的名字就是技能的名字。文件夹里最重要的是一个叫 `SKILL.md` 的文件。

```text
~/.dsh/skills/
├── 我的技能一/
│   └── SKILL.md
├── 我的技能二/
│   ├── SKILL.md
│   └── 模板.md          ← 技能也可以带自己的附属文件
└── 别人的技能/
    └── SKILL.md
```

`SKILL.md` 的结构分两部分：开头是给机器看的信息，下面是给人看的内容。

开头那部分用三个减号包起来，格式是固定的：

```text
---
name: 技能的名字
description: 一句话说明它做什么、什么时候该用
---
（下面是正文，用普通文字写）
```

`name` 和 `description` 这两行必须写，而且必须放在文件最开头。写错格式这个技能就不会被加载，后面 4.9 节会讲怎么排查。

### 4.2.1 一个关键机制

平时进 AI 视野的是技能名和 description 这两样，正文一个字都不占地方。 它平时看到的是所有技能的一句话摘要，像一本书的目录。只有当你的任务和某个摘要对得上，它才会去读那个技能的全文。

所以：

- `description` 决定它会不会被用上。
- 正文决定它做得好不好。

但它也不是越多越好。 摘要虽然短，装到几十上百个时目录也会变长，它挑错技能的几率会上升（4.9 节末尾会讲怎么清理）。

这两件事要分开考虑。一个技能写得再好，`description` 写得不对，它一辈子也不会被触发。

## 4.3 description 决定它会不会被用上

写 `description` 的正确思路是：写触发词，不写功能简介。

对比一下：

不好：

```text
description: 帮助处理文档
```

问题在哪：「处理文档」太笼统了。什么算文档？处理是转格式、还是总结、还是校对？AI 拿这句话去判断「这次的任务要不要用这个技能」，判断不出来。

好：

```text
description: 把 PDF 或 Word 课件转成结构化的复习提纲，包含知识点标题、要点列表和自测题。当用户说「转成复习提纲」「整理课件」「提取知识点」时使用。
```

好在哪：它写清了三件事——输入是什么（PDF 或 Word 课件）、输出是什么（复习提纲，含标题、要点、自测题）、用户会怎么开口（那些触发词）。

最后那一点最容易被忽略，但它恰恰是最有用的。把你平时会说的那几句话原样写进去，命中的概率会高很多。

写 `description` 的三个要点：

1. 说明输入是什么（什么类型的文件、什么场景）。
2. 说明输出是什么（做成什么样）。
3. 列出你会说的话，也就是触发词，三到五个就够。

## 4.4 手把手写第一个技能

现在写一个真的。选一个你确实会反复做的任务——下面用「把课件 PDF 转成复习提纲」做示范，你可以照着改成自己需要的。

### 第一步：把文件夹建好

在 `~/.dsh/skills/` 下面新建一个文件夹，名字用英文小写加连字符，例如 `course-to-outline`。

为什么用英文名：中文文件夹名在一些工具里会出现编码问题。技能名用英文更稳妥，技能内容用中文完全没问题。

### 第二步：把 SKILL.md 写出来

在文件夹里新建 `SKILL.md`，内容如下。这份可以直接改着用：

保存这一步有个坑：用记事本时，把「保存类型」改成「所有文件」，文件名整个写成 SKILL.md——否则会存成 SKILL.md.txt，技能不会被加载。技能名（文件夹名和 name 那一行）只能用小写英文、数字和连字符，例如 course-to-outline；写成中文或其他符号，技能一样加载不了。

```text
---
name: course-to-outline
description: 把 PDF 或 Word 课件转成结构化的复习提纲，包含知识点标题、要点列表和自测题。当用户说「转成复习提纲」「整理课件」「提取知识点」「做复习资料」时使用。
---
# 课件转复习提纲
## 什么时候用
用户提供了一份课程课件（PDF 或 Word），并且希望得到一份可以用于复习的提纲。
## 什么时候不要用
- 用户只是想问课件里的某个具体问题 —— 直接回答即可，不要生成整份提纲。
- 用户要的是逐字转录 —— 这个技能做的是提炼，不是抄录。
## 步骤
1. 确认文件位置。如果用户没有说明文件在哪，先询问文件的完整路径，不要自己猜。
2. 读取文件，先报告你识别到的结构：一共多少页、分成几个章节、每章大致讲什么。
   报告之后等用户确认，再继续下一步。
3. 按章节整理知识点。每一章输出：
   - 一个章标题
   - 三到八条要点，每条不超过两句话
   - 如果这一章有公式或定义，单独列出来
4. 为每一章生成三到五道自测题，题型以简答为主。
5. 把所有内容写进一个 Markdown 文件，文件名格式为 `复习提纲-课程名.md`，
   保存到当前工作区。
## 产出要求
- 全部用中文。
- 不要使用课件里没出现的概念。课件没讲到的内容不要补充。
- 不要用「综上所述」「由此可见」这类填充词。
- 要点必须是完整的句子，不要只写关键词。
- 如果某一页内容识别不清，在文件末尾单独列一节「识别不清的部分」，
  说明是第几页，不要猜内容。
## 自检清单
写完之后逐条检查：
- [ ] 每一章都有标题、要点和自测题
- [ ] 没有出现课件里没有的概念
- [ ] 自测题都能在提纲里找到答案
- [ ] 文件已经保存到工作区，文件名符合要求
- [ ] 识别不清的部分已经单独列出，没有猜测
## 如果做不到
- 文件读不出来（加密、扫描版无文字层）：告诉用户原因，建议先做文字识别，不要假装读到了内容。
- 文件太大超出处理上限：先处理前半部分，告诉用户还剩多少没处理，询问是否继续。
- 用户没说文件在哪：询问，不要在工作区里随便找一个文件开始做。
```

### 第三步：看看这份技能为什么这么写

对照着看，每一部分都有明确作用：

| 部分 | 作用 |
|---|---|
| description | 决定它会不会被触发。里面写进了「转成复习提纲」「整理课件」等原话 |
| 什么时候用 | 进一步限定触发场景 |
| 什么时候不要用 | 防止误触发。 这一节最容易被省略，但很关键 |
| 步骤 | 具体动作。第 2 步「先报告结构、等确认」是防止它一口气做完发现方向错了 |
| 产出要求 | 输出格式和风格约束。这里的每一条都对应一个你曾经不满意的点 |
| 自检清单 | 让它自己先检查一遍，能拦掉大部分低级错误 |
| 如果做不到 | 失败处理。没有这一节，它在做不到时会开始编 |

注意「产出要求」那一节。 里面「不要使用课件里没出现的概念」「不要用填充词」「要点必须是完整句子」这几条，都不是凭空写的——它们对应的是 AI 最常见的几个毛病。你写技能的时候，就回想自己上次不满意的地方是什么，把那一条写进去。

### 第四步：装上并验证

技能文件夹放好之后，按 3.7 节最后一步重启并刷新，然后确认它出现了。

「在哪里确认」这个问题，不同版本叫法不一样（有的叫「技能」，有的在「设置」里，有的和插件放在一起）。你不用记名字，记住两件事就行：

1. 先找带「技能」两个字的地方——一般在设置里，或者插件列表旁边。
2. 找不到就直接问它：「我刚放了一个技能，叫什么什么名字，我在界面里去哪能看到它？」——它就在这个界面里，回答比书上准。

验证方式很重要：用一个不提技能名字的任务去试。

不要说「用课程转提纲技能帮我做一下」，那不算验证——你直接点名了，它当然会用。要说：

这是我的近代史课件，帮我整理一份复习资料。

如果它按步骤先报告了结构、然后等确认，说明技能生效了。如果它直接开始大段输出，说明没触发，看 4.9 节排查。

## 4.5 写技能的六条规矩

写完第一个之后，后面都按这六条来。

一、`description` 写触发词，不写功能简介。

把你会说的原话写进去。三到五个触发词。

二、步骤必须是可执行的动作，不是形容词。

不好：「仔细分析课件内容」——什么叫仔细？它不知道。

好：「先报告文件总页数和章节划分，等用户确认再继续」——这是一个可以执行的动作。

三、每一步都要能验收。

每一步最好有一个明确的结果。含糊的步骤会让它自由发挥，而自由发挥就意味着每次结果都不一样。

四、必须写失败处理。

「如果做不到」这一节不能省。没有它，它在读不到文件的时候会开始猜内容——猜出来的内容看起来很正常，这才是最危险的。

五、写清用哪些文件、产出放哪。

文件路径、文件名格式、保存位置都要写明。否则你每次都要去找它把文件存哪了。

六、删掉正确但没用的废话。

「请认真对待这个任务」「务必保证质量」这类话没有任何作用，只会占位置。写具体的约束，不写态度要求。

## 4.6 先认识 GitHub

装技能只有两条路：把仓库地址给它，或者用内置的插件市场。地址来自 GitHub，所以先花几分钟认识这个网站。

### 4.6.1 GitHub 是什么

GitHub 是一个存放文件、并且记录每次改动的网站。上面的东西默认公开，谁都能看、能下载，下载公开仓库不需要注册账号。

它的基本单位叫「仓库」（repository，简称 repo），就是一个文件夹。 一个技能占一个文件夹，所以找技能就是在找一个仓库。

GitHub 是英文界面。看不懂就用浏览器的翻译：在页面上点右键，选「翻译成中文」。

### 4.6.2 怎么找

搜索框在页面左上角，用法和百度一样，直接搜关键词。能用的词：

```text
dsh skill
dsh 技能
awesome dsh
```

有个约定值得记住：仓库名以 `awesome-` 开头的，一般是某个领域的人工精选清单，不是随手收的。这类仓库适合翻着找。

### 4.6.3 怎么判断一个仓库靠不靠谱

找到之后别急着用。仓库页面上有四个地方值得看：

| 看什么 | 在哪 | 说明什么 |
|---|---|---|
| README | 页面往下滚 | 这个项目做什么、怎么用。先读它 |
| Stars | 仓库名下方，一个星形图标 | 有多少人收藏。数字大说明用的人多 |
| 最近一次更新 | 文件列表上方 | 半年以上没动过的，谨慎 |
| Issues | 顶部标签 | 别人遇到的问题。看看有没有你正担心的那类 |

### 4.6.4 怎么把文件拿下来

从仓库直接下载： 点绿色的 `Code` 按钮 → `Download ZIP`，解压就行。

从 Releases 下载打包好的版本： 仓库顶部如果有 `Releases` 标签，说明作者发布了可以直接用的成品。点进去，展开 `Assets`，会看到一堆文件名——按「系统 + 芯片 + 格式」三步筛：

| 你的电脑 | 文件名里会出现 |
|---|---|
| Windows（绝大多数） | windows 或 win，加 x64，后缀 .exe |
| Mac（M1/M2/M3） | mac 或 darwin，加 arm64，后缀 .dmg |
| Mac（Intel） | mac，加 x64，后缀 .dmg |
| Linux | linux，后缀 .AppImage 或 .deb |

不知道自己 Mac 是哪种芯片：点左上角苹果图标 →「关于本机」，写 Apple M 开头的选 `arm64`，写 Intel 的选 `x64`。

Assets 里还有两个文件叫 `Source code (zip)` 和 `Source code (tar.gz)`——那是源代码，不用下。

### 4.6.5 被系统拦住是正常的

从 GitHub 拿到的文件多半没有花钱买数字签名，所以：

- Windows 会弹「Windows 已保护你的电脑」，点「更多信息」→「仍要运行」。
- Mac 会说来自身份不明的开发者，去「系统设置」→「隐私与安全性」，点「仍要打开」。

前提是你确认过这是官方仓库发布的。 从群里、网盘拿到的同名文件，看到这个提示就该停下来。

## 4.7 附赠：去 GitHub 找现成的技能并装上

自己写技能需要一点时间。但已经有很多人把自己写的技能公开出来了，你可以直接用。

技能本质上就是一个文本文件，没有编译、没有安装程序，所以分享和安装都特别简单：你直接把地址丢给它就行。

### 4.7.1 最简单的装法：直接让它装

不要在界面上找按钮，也不要自己下载文件。 把地址给它，说一句话：

```text
请访问 https://github.com/作者/仓库 ，看一下里面的 SKILL.md，
告诉我它是做什么的、有没有风险。我确认之后，帮我装到 ~/.dsh/skills/ 下，
装完告诉我怎么验证它生效了。
```

它自己会做这些事： 读那个仓库、把技能文件放到正确的位置、必要时重启服务，然后把结果告诉你。

三个要点：

1. 先让它说清「这是干什么的、有没有风险」，你再点头。 上面那句话就是按这个顺序写的——对陌生仓库不要直接说「帮我装」。
2. 装完让它告诉你「怎么验证」。 它可能会说「重启后拿一个相关问题试试」，照做就行。
3. 不确定的技能，宁可不装。 判断标准见 4.7.3。

### 4.7.2 去哪里找：让它帮你搜

先说一句：你甚至不必先去 GitHub 搜。 直接问它：

```text
我想找一个能做「把 PDF 转成复习提纲」的技能。
先告诉我 GitHub 上有哪些可选、各自是什么来源，我选了之后你再装。
```

注意这里的分寸：让它先把候选和来源列出来，你挑一个，再让它装。不要一上来就说「随便找一个帮我装上」。

也可以自己搜。在 GitHub 的搜索框里搜这些关键词：

```text
dsh skill
dsh skills
awesome dsh skills
dsh 技能
```

搜出来的结果大致分三类，判断方式不太一样：

第一类：技能合集。

一个仓库里装了很多个技能。例如 `imsai-sh/awesome-deepseek-harness-plugins` 这样按目录整理、收录四千多个插件的。这类适合逛一逛，挑自己需要的。

第二类：技能管理插件。

这不是技能，而是一个管理技能的插件——装上之后你可以在界面里搜索、一键安装、查看已装的技能。例如 `dsh-market/dsh-market`。DSH Desktop 内置的插件市场就在这一类里，不用再另外装一个。

第三类：单个技能。

某个工具或服务配套的一个技能，给特定服务用的，只有你正好用那个服务时才需要。

必须说明：上面这些是社区项目，随时可能改名、停止维护或改变内容。本书核对日期是 2026 年 9 月。不要因为书里提到就默认它可靠——按下面 4.7.3 的四条自己判断一遍。

### 4.7.3 装之前先判断能不能装

装技能等于让一段陌生文字进入你的 AI 的决策过程，有些技能还会让它运行命令。所以装之前花一分钟看四件事：

一看：有没有 `SKILL.md`，格式对不对。

打开仓库，找到 `SKILL.md`，看开头是不是 `name` 和 `description` 两行，包在三个减号中间。格式不对的技能根本不会被加载，装了也没用。

二看：最近一次更新是什么时候。

在仓库页面上能看到最后一次提交的时间。半年以上没动过的要谨慎——工具在变，老技能里的步骤可能已经失效了。

三看：它需要什么。

读一遍正文，回答三个问题：要不要额外装东西？要不要联网？要不要你自己的 Key？需求的越多，出问题的可能性越大。

四看：正文里有没有危险动作。

重点找这些词：删除、清空、格式化、覆盖、修改系统设置、发送到网络。如果正文里让它删文件或者改系统配置，不要装，除非你能读懂它在做什么并且确认没问题。

判断规则是这样：

四条都过 → 可以试。有一条不确定 → 先不装。

或者先问你的 AI：「看一下这个仓库的 SKILL.md，它要做什么？有没有风险？」

### 4.7.4 另外两种装法（一般用不上）

最省事的是让 AI 直接装（4.7.1）。下面这两种是备选：一个用来逛，一个在 AI 装不了的时候兜底。

插件市场。 DSH Desktop 内置了插件市场（第 3.7 节），可以在里面浏览、看详情、一键安装。适合漫无目的地逛一逛，看看别人都在做什么。

手动放进去。 只有当你想装的技能 AI 装不了（比如网络不通、仓库本身有问题）时才用。如果你电脑上有 git：

```text
cd $HOME\.dsh\skills
git clone 仓库地址
```

没有 git 也不影响，用网页下载就行：

1. 在 GitHub 仓库页面找到绿色的 `Code` 按钮。
2. 点它，选择 `Download ZIP`。
3. 解压下载的文件。
4. 解压后找到包含 `SKILL.md` 的那一层文件夹，整个复制到 `~/.dsh/skills/` 下面。

第 4 步是新手最容易出错的地方，单独强调一次。

### 4.7.5 最常见的错误：多套了一层文件夹

这是手动装技能失败的第一大原因，几乎每个人都会遇到一次。

出错的形态：

```text
~/.dsh/skills/
└── awesome-dsh-skills-main/      ← 多出来的这一层
    └── pdf-to-notes/
        └── SKILL.md
```

正确的形态：

```text
~/.dsh/skills/
└── pdf-to-notes/
    └── SKILL.md
```

从 GitHub 下载的压缩包解压后，通常会自带一层 `仓库名-main` 这样的文件夹。如果你把整个解压结果直接复制进去，就多了一层，DSH 在里面找不到 `SKILL.md`，技能不会被加载。

判断标准只有一条：

`~/.dsh/skills/<技能名>/SKILL.md` —— 必须正好是这个层级。

装完之后按 3.7 节最后一步重启并刷新，和自己写技能时是同一步。

### 4.7.6 装完怎么验证它真的生效了

三步：

1. 看列表。 在带「技能」字样的那个地方（怎么找见 4.4 节）能看到它。
2. 看触发。 用一个和 `description` 对得上的任务去试，不要提技能的名字。
3. 看过程。 如果它做了技能里特有的动作——比如那个课件技能会先报告章节结构——就说明技能被加载了。

第 3 步是最可靠的证据。光在列表里看到它，只能说明文件放对了位置，不能说明它会被触发。

### 4.7.7 装上了但不生效

按顺序排查这四条：

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 列表里根本没有它 | 文件夹层级套错了 | 回到 4.7.5，检查 SKILL.md 的层级 |
| 列表里有，但从不触发 | description 和你的说法对不上 | 改 description，把你自己的原话加进去 |
| 改完还是没反应 | 没重启 | 按 3.7 节最后一步重启并刷新 |
| 触发了，但行为不对 | 和已有技能撞了 | 看是不是有两个技能抢同一件事，删掉一个或改掉触发词 |

### 4.7.8 想把自己写的技能分享出去

第 4.9 节之前先说这一条，因为分享前有一件事必须做。

分享前脱敏三件事：

1. 你自己的文件路径。 技能里经常写着 `C:\Users\你的名字\...`，这暴露了你的用户名。
2. Key 和其他凭据。 检查正文里有没有粘贴过 API Key。
3. 内部资料。 课程名、老师名、同学姓名、内部通知，这些都不该出现在公开仓库里。

做法就是通读一遍：把技能从头读到尾，把上面三类内容换成占位符。读一遍就够——但一定要读，不要直接上传。

## 4.8 让 AI 帮你写技能

有个省力得多的做法：不要从空白开始写，让它把刚才那次成功的做法回写成技能。

做法是，一件任务做完并且你满意之后，跟它说：

把刚才这次的做法整理成一个技能，写到 `~/.dsh/skills/` 下。

要求：`description` 里写上我会说的那几句话；步骤写成可执行的动作；

加上产出要求和自检清单；再加上一节「如果做不到」。

写完告诉我这个技能会在什么情况下被触发。

这个做法好在哪：它已经知道刚才每一步实际是怎么做的，包括用了哪些文件、遇到了什么问题、怎么绕过去的。这些细节你自己回忆反而容易漏。

它写完你还要做一件事：通读一遍，删掉多余的部分。 它通常会写得偏长，把一些不重要的步骤也写进去。技能不是越长越好，长了反而容易跑偏。

另外，过一段时间可以让它做一次体检：

检查 `~/.dsh/skills/` 下所有的技能，告诉我哪些内容重复了、

哪些步骤可能已经过时、哪些从来没有被触发过。

重复的合并，过时的修掉，从没触发过的考虑删掉——一个从没被触发过的技能，大概率是 `description` 写得不对，或者这个需求根本不存在。

## 4.9 出问题怎么办

症状一：写了技能，但它从来不触发。

原因几乎总是 `description`。改法：把你实际会说的那句话原样加进去。还有一个可能：文件开头的三减号格式写错了，或者 `name`、`description` 前面有空格、有空行。格式错误会导致技能被静默忽略，不会报错。

症状二：它在不该用的时候用了技能。

原因是你没写「什么时候不要用」那一节。补上它，写清哪些相关但不适用的情况。

症状三：装了技能之后对话变慢了。

装太多技能会变糊涂，不是因为慢。 技能本身占不了多少地方（原因见 4.2.1 节）。但装得多了，交给 AI 的那份「技能目录」就越长，它挑错技能的几率会上升——你想用 A 技能，它却用了长得很像的 B 技能。

所以清理的标准还是那一条：三个月没用过的，删。

症状四：技能和插件冲突，行为混乱。

两个东西在抢同一件事。先禁用一个，看行为是否恢复正常，用这个办法定位是哪一个的问题。

症状五：技能里引用的文件找不到。

技能正文里写了一个附属文件（比如模板），但那个文件没跟着一起放进来。检查文件夹里是不是齐的。

## 本章验收

这一章有两个验收，都要做。

验收一：自己写一个技能，并且它被自动触发。

用 4.4 节的方法，为一件你反复做的事写一个技能。然后用一个不提技能名字的任务去试，确认它按技能里的步骤做了。

验收二：从 GitHub 装一个别人的技能，并且确认生效。

按 4.7 节走一遍。重点确认两件事：`SKILL.md` 的层级正确，以及它真的会被触发。

验收：写出一个自己的技能并在陌生任务里被自动触发，并且从 GitHub 装上一个别人的技能并确认生效。

做完这两个验收，你就掌握了这本书里最实用的一项能力。下一章讲评审团——它是用来检查你自己作品的质量的。
