本章要解决的问题：前面几章教你把它装好、配好、怎么操作。从这一章开始，讲的是用起来之后的事——它报错了怎么办、会话该怎么管、钱花到哪里去了、话该怎么说清楚。

报错、会话、花钱这三件事都不难，但它们有一个共同点：不处理就会一直消耗你。

同一件事，有人一次就做对，有人来回改十遍。差别通常不在谁的电脑好、谁充的钱多，而在怎么说。

这一章没有需要提前准备的东西，随时可以回来查。

## 7.1 卡住了怎么求助

你遇到的大部分报错，别人早就遇到过了。 报错信息不是给你看的判决书，是给程序看的诊断记录——它里面通常已经写明了哪里出了问题。

问题在于，大部分人求助的时候，把最有用的那部分信息丢掉了。

### 7.1.1 报错信息要连原文一起给，不要自己转述

这是本节最重要的一条。

错误做法（转述）：

我装那个东西的时候报错了，好像是什么权限的问题，你帮我看看。

正确做法（原文）：

我按教程执行 `npm install -g openclaw@latest`，报错如下：

```text
npm error code EPERM
npm error syscall mkdir
npm error path C:\Program Files\nodejs\node_modules\openclaw
npm error errno -4048
```

我期望它正常安装完成。

为什么转述会失败：你会顺手漏掉它需要的关键细节。 上面那个例子，「权限问题」这四个字没有信息量；真正有用的是 `EPERM`、`mkdir` 和那行路径——它们直接指向原因：往一个需要管理员权限的目录里写东西被拒绝了。

关键线索往往正好在你省略掉的那几个词里。

还有两种常见的丢信息方式：

- 只截一半。 报错通常有好几行，最后一行往往是结论，中间几行才是原因。整段复制。
- 不说自己在做什么。 同一个报错，在安装时出现和在运行项目时出现，原因是完全不同的。把你刚才执行的命令一起给出。

### 7.1.2 一条可以直接用的求助模板

把下面这段存下来。以后遇到问题，照这个格式填，填完发给你的 AI。

```text
我在做什么：
（一句话，例如：正在安装 OpenClaw）
我执行的命令或操作：
（把刚才敲的命令、或者点的地方写清楚）
我期望的结果：
（例如：看到安装完成，然后能运行 openclaw --version）
实际发生的结果：
（例如：命令跑到一半停住，出现下面这段报错）
完整报错（原文粘贴，不要删减、不要转述）：
我已经试过：
（做过什么、结果如何。没试过就写「还没试过」）
```

每一行为什么必须写：

| 这一行 | 它解决了什么 |
|---|---|
| 我在做什么 | 同一个报错在不同场景下原因不同，AI 需要知道上下文 |
| 执行的命令 | 让 AI 能直接看出命令本身有没有写错 |
| 期望的结果 | 让 AI 知道什么是「正常」，否则它无法判断偏差在哪 |
| 实际的结果 | 描述现象，帮 AI 定位是卡住、报错还是静默失败 |
| 完整报错 | 最有价值的一行。 关键词都在这里 |
| 我已经试过 | 防止 AI 让你重复你已经做过的事 |

最后一行特别容易被忽略。写「还没试过」也没关系，但如果你已经试过某几种办法，一定要写——否则 AI 会从头开始给你建议，而你只能一条条回「这个我试过了」。

### 7.1.3 怎么判断是「我错了」还是「教程过时了」

这是新手最容易搞错的一件事。很多人遇到报错的第一反应是「我太笨了」，然后反复重试同一个步骤，浪费一两个小时。

正确的第一反应是：先怀疑教程，再怀疑自己。 这类工具更新很快，一本三个月前写的教程，里面的命令可能已经不适用了。

但也不能一路怀疑到放弃。用下面这张表快速定位：

| 报错里的特征 | 大概率是什么问题 | 先去查什么 |
|---|---|---|
| 提到版本号不满足 | 教程或软件的版本要求变了 | 官方文档的系统要求 |
| 提示某个参数、选项不存在 | 教程过时 | 官方文档的命令参考 |
| 提示端口被占用 | 你电脑上的环境问题 | 换个端口，或关掉占用它的程序 |
| 提示权限不足、被拒绝 | 权限或安全软件 | 是否需要管理员权限、杀软是否拦截 |
| 提示「不是内部或外部命令」 | 环境变量 PATH 问题（只有命令行版和 OpenClaw 需要处理，桌面版可以忽略） | node -v、npm prefix -g、PATH |
| 完全看不懂 | 不要猜 | 把原文交给 AI，并说明你在做什么 |

倒数第二行值得单独记一下：在系统终端里报「不是内部或外部命令」，几乎总是 PATH 问题，也就是「装了，但系统不知道装在哪」。这是 Windows 上最高频的一类报错，第 2 章给过排查命令。用桌面版的话，这一条可以直接忽略——桌面版的操作都在界面里完成，不依赖命令行。

### 7.1.4 教程过时的五个信号

看到下面这些信号，先把教程和你的操作各怀疑一遍：

1. 版本号对不上。 教程说适用于 1.x，你装的是 3.x。
2. 端口号变了。 教程让你访问 3000，程序实际打印的是另一个。
3. 包名变了。 教程里的包名在安装时报「不存在」。
4. 截图和你看到的界面不一样。 菜单里根本没有教程说的那一项。
5. 命令参数不存在。 报错说「未知选项」。

这五条对应同一个结论：软件变了，教程没跟上。 这时候要做的是去找官方文档，或者直接问 AI「这个版本的等价做法是什么」，而不是反复重试旧命令。

### 7.1.5 AI 也答不上来的时候

有时候你把报错原文给了 AI，它给的建议试了没用。按下面的顺序处理：

1. 换一个问法。 把「怎么解决这个报错」换成「这个报错说明发生了什么」，先让它解释原因。
2. 让它先复述你的问题。 说「你先复述一遍我在做什么、卡在哪」，能立刻发现它是不是理解偏了。
3. 开一个新会话重新问。 旧会话里可能已经堆了一堆错误信息，把它带偏了。第 7.2 节会讲这件事。
4. 去官方文档。 搜「官方文档 + 你的报错关键词」通常比搜报错本身更有效。

一条纪律：同一个问题问了三次还没解决，就换路径。 换个方法做、换个教程看、或者先跳过这一步做别的。在原地反复试最消耗人，而且往往越试越乱。

### 如果这一步没成功

情况一：我不知道该复制哪段报错。

整个窗口的内容都复制。AI 能自己挑出有用的部分，你不需要替它筛选。

情况二：报错窗口一闪就没了。

说明程序启动后立刻退出了。在终端里手动运行同一个命令，报错就会留在屏幕上。

情况三：我不知道怎么复制终端里的内容。

在终端窗口里用鼠标选中文字，然后按 `Ctrl+C`，或者直接右键选择「复制」。选中之后粘贴到 AI 的对话框里即可。

验收：用 7.1.2 的模板成功解决过一个真实报错，并把它记了下来（记在哪都行；第 7.8.3 节会教你建一份正式的环境档案）。

## 7.2 会话怎么管

### 7.2.1 会话是什么

一次连续的对话就是一个会话。

会话最需要理解的特点：它只记得这个会话里说过的话。 你开一个新会话，它对你的项目、你的偏好、你刚才解释过三遍的要求，一无所知。

这个特点有好处也有坏处。好处是干净——新任务不受旧任务干扰。坏处是你得重讲一遍要求。

### 7.2.2 怎么开一个新会话

下面反复会出现「开一个新会话」，先把这个动作教会你。

大致位置：会话列表一般在界面的侧边或顶部，附近会有一个「新建」「新会话」或者一个「＋」号。点它，就开了一个干净的会话。

界面上的具体文字和位置会随版本变化，所以这里不写死。 找不到的时候，用这本书里最省事的办法——直接问它：

```text
我不知道怎么在界面里开一个新的会话。请告诉我应该点哪里，说得具体一点。
```

它就在这个界面里，它的回答比书上写得准。

找到之后把位置记住，因为这个动作你以后会经常用——第 7.1.5 节、第 6.4 节都要用到它。

如果你确实找不到任何「新建会话」的入口，还有一个笨办法：在会话列表里找最近一个你不用的旧会话，直接在那个里面继续。效果差一些（它还记得旧内容），但比继续在已经带偏的会话里问要好。

### 7.2.3 什么时候该开新会话

四条判断标准，满足任意一条就开新会话：

1. 换任务了。 上一件事是整理课件，这一件事是写文案——两者要求完全不同，混在一起它容易串味。
2. 它开始答非所问。 明明说清楚了，它回的却是上一个问题的延续。
3. 它反复犯同一个错。 你纠正过两次，它还是那样。这时候继续纠正往往没用，因为它已经把错误做法当成前提了。
4. 明显变慢了。 会话很长之后，它的响应会变慢。

判断口诀：新任务、新会话。 这一条能解决新手遇到的一大半「它怎么变笨了」的问题——它不是变笨了，是被前面的内容干扰了。

### 7.2.4 为什么会话太长会变糊涂

不是它「忘了」，而是早期说过的话被压得很淡了。

会话里的内容是有长度上限的。当内容接近上限时，系统会对早期的部分做压缩，保留大意、丢掉细节。你最开始强调的那句「不要用专业术语，我在给新生讲」，在压缩之后可能就只剩下一个模糊的印象。

所以会话越长，你最早提的要求越容易被冲淡。这不是缺陷，是长度限制下的必然结果。

实用的做法： 一个会话专注做一件事，做完就结束。别把一个会话当成常驻的记事本。

### 7.2.5 怎么让它长期记住你的偏好

这里要分清两件事：

|  | 会话记忆 | 长期记忆 |
|---|---|---|
| 有效期 | 只在这个会话里 | 跨会话有效 |
| 怎么来 | 你在这个会话里说的 | 记忆类插件，或者写进技能 |

如果你有一批稳定的要求——比如「我是大一新生，解释的时候不要用行话」「回答用中文，不要写太长」——每次都重说一遍是很浪费的。

两种解决办法：

1. 装一个带记忆功能的插件。 这类插件的作用就是把某些信息跨会话保留下来。装上之后，你告诉它「记住这一条」，下次新会话它就还知道。
2. 写进技能。 如果这个要求是针对某一类任务（比如「所有给同学看的文档都要这样写」），那它更适合写成技能。第 4 章会专门讲。

装记忆类插件时的注意事项和第 3.7 节一样：插件是别人写的代码，装之前看清来源和权限。记忆意味着信息被长期保存下来，所以不要让它记录你的密码、身份证号这类内容。

### 7.2.6 会话占空间怎么清理

会话记录会一直存在你的电脑上。日积月累之后，它可能占掉不少空间。

清理的位置在 `~/.dsh/sessions/` 目录下（Windows 上是 `C:\Users\你的用户名\.dsh\sessions\`）。界面上通常也有会话列表可以删除。

删除之前必须知道一件事：删掉会话，就等于删掉那段对话的完整记录。 如果里面有它还写过什么、你当时的原始要求，这些都会一起消失。

### 7.2.7 一条硬纪律

重要的产出，永远先存成文件，不要只留在对话里。

这是本节最值钱的一句话。

很多新手做完一件事，成果只存在于对话记录里。等哪天会话删了、软件重装了、电脑换了，成果就没了。而且只留在对话里的东西，你下次也没法直接引用。

做法就一句话： 每做完一件有价值的事，跟它说一句「把上面的结果存成文件，放在工作区里」。它会自己写文件。这个文件才是你的成果，对话只是过程。

### 如果这一步没成功

情况一：我不知道现在这个会话是什么时候开始的。

大部分界面会显示当前会话的标题或时间。找不到也没关系，直接开一个新会话就行，不会有损失。

情况二：开新会话之后，它什么都不知道了。

这是正常的。你可以把你之前存下来的文件直接给它：「看一下 `笔记.md`，然后接着做」。这也是为什么上一条纪律那么重要——文件就是你跨会话的传递方式。

情况三：删错了会话。

`~/.dsh/sessions/` 里的内容如果做过备份，可以从备份恢复。没备份就恢复不了。

验收：能判断一个任务是该开新会话还是接着聊，并且你最近一次任务的结果已经存成了文件。

## 7.3 花钱怎么控制

### 7.3.1 先弄清计费的三条规则

理解这三条，后面所有省钱方法你都能自己推出来。

规则一：按 token 计费，输入和输出分开算。

token 是模型处理文字的最小单位。官方给的比例大致是：一个中文字符约 0.6 个 token（一千个汉字大约六百个 token），一个英文字符约 0.3 个。你发过去的内容算输入，它答回来的内容算输出，两者价格不同。

规则二：输出比输入贵得多。

这是最重要的一条。以 `deepseek-flash` 为例，输出价格是输入（未命中缓存）的 4 倍，是输入（命中缓存）的 200 倍。

规则三：分高峰和空闲两种价格，空闲是高峰的一半。

高峰时段是北京时间周一至周五 9:00–12:00、14:00–18:00。其余时间——晚上、周末、工作日的午休和傍晚——都算空闲。

### 7.3.2 官方价格表，以及从里面读出的三件事

DeepSeek 官方的价格是公开的。单位是「元／百万 tokens」（出处：官方「模型 & 价格」页，核对日期 2026-09）：

|  | deepseek-flash 空闲 | deepseek-flash 高峰 | deepseek-v4-pro 空闲 | deepseek-v4-pro 高峰 |
|---|---|---|---|---|
| 输入（命中缓存） | 0.02 | 0.04 | 0.15 | 0.30 |
| 输入（未命中缓存） | 1 | 2 | 4.5 | 9.0 |
| 输出 | 4 | 8 | 13.5 | 27.0 |

价格随时可能调整，以官方「模型 & 价格」页面为准。 下面这三条是从上面这张表里读出来的。

第一，缓存命中和未命中差了 50 倍。

「缓存命中」指的是：你这次发的内容里，和之前发过的部分重复的那一段。重复的部分会自动走缓存价。

这一条修正了一个常见的误解：反复使用同一份材料，没有你想的那么贵。 第一次读是原价，后面再读同一份，大部分内容走缓存价。

所以「把材料存成文件、后面引用文件」这个习惯仍然值得养成——但它省的是会话管理上的麻烦（第 7.2.7 节），而不是省钱的主要手段。

第二，输出才是开销的大头。

按空闲价，输出 4 元，输入未命中才 1 元。这意味着：让它少写废话，比让它少读材料更省钱。 具体怎么加输出约束，见 7.3.6 第一条。

第三，空闲时段直接打五折。 时段划分见 7.3.1 规则三。对学生来说这条几乎没有成本——你本来就不太可能在周五下午两点集中干活。

### 7.3.3 怎么设置上限

大多数模型提供商的后台都提供用量提醒或额度限制。设置方式各平台不同，但思路是一样的：

1. 找到用量或额度相关的设置。
2. 设一个提醒阈值（比如用量达到一半时通知你）。
3. 如果你容易忘记，直接设一个额度上限。上限的作用不是省钱，是防止意外——比如 Key 泄露被刷、或者某个任务陷入循环反复运行。

建议在第一次充值时就把提醒设上。 这时候设置成本最低，而且你会立刻知道自己的使用节奏。

### 7.3.4 什么任务用哪个模型

官方目前只有两个模型可选，所以这个问题比想象中简单：

| 任务类型 | 用哪个 |
|---|---|
| 要读图片、截图、扫描件 | 只能 deepseek-flash |
| 格式整理、分类、改写、翻译短句、简单问答 | deepseek-flash |
| 写文档、分析资料、解释概念 | deepseek-flash 先试 |
| 复杂推理、多步骤项目、反复做不满意 | 换 deepseek-v4-pro |

做法就是第 3.2 节的结论：默认设成 `deepseek-flash`，难题临时换 `deepseek-v4-pro`，做完换回来。

一个常见的浪费是：用 `deepseek-v4-pro` 去做「把这份名单按拼音排序」这种活。这不是奢侈，是没必要——而且它还不支持读图。

### 7.3.5 三档用量，对号入座

不给金额，因为金额取决于你的实际用法。给形状：

| 用量档位 | 典型使用方式 | 你该做什么 |
|---|---|---|
| 轻度 | 偶尔问问题、改改文案、解释概念 | 不用管 |
| 中度 | 经常处理文档、整理资料、写作业草稿 | 每月看一次用量 |
| 重度 | 天天做项目、处理长文档、跑多轮任务 | 设上限，并把大任务挪到空闲时段 |

准确的做法是看你自己的用量页面。 平台后台会显示已用量和余额，那是最可靠的信息来源。

### 7.3.6 五个省钱习惯

按效果从大到小排。前两条比后三条管用。

一、让它少写废话。 输出是最贵的一项。加输出约束：「只要结论，不要复述我的问题」「用列表，每条不超过一行」「不要写总结段」。

二、把大任务挪到空闲时段。 处理长文档、做整章整理这类耗时任务，安排在晚上。

三、让它先追问、先给方案，再动手。 返工是最贵的浪费——它理解错方向做了一大堆，你重讲一遍再来一次，两轮的输出费用都是你付。花三十秒回答它三个问题，能省掉一整轮。

四、能一次说清就别挤牙膏。 分五轮慢慢补充要求，比一开始就说清楚贵，因为每一轮都要带上全部历史。

五、每月看一次用量。 不需要精细记账，看一眼总数和主要花在哪类任务上就够了。

### 如果这一步没成功（指省钱没效果）

情况一：我已经按上面做了，还是花得快。

检查是不是有任务陷入了循环——它反复做同一个动作停不下来。发现这种情况立刻中断它。

情况二：我不知道该在哪里看用量。

登录你申请 Key 的那个平台，找「用量」「账单」或「费用」相关的页面。查不到就搜「平台名 + 用量查询」。

情况三：我担心 Key 泄露被别人用。

立刻去平台后台删除旧 Key、新建一个。删旧的这一步很重要，光建新的不够，因为泄露的那个还能用。不要把完整的 Key 发给任何人，排查问题时也不要贴出来。

验收：你能在自己的平台上找到用量页面，说得出到目前为止花了多少、主要花在哪一类任务上，并且已经设置了用量提醒。

到这里，「别把事情搞砸」的部分讲完了。下面八节讲怎么把它用得更好。

## 7.4 让 AI 先追问，再动手

### 7.4.1 它最常见的失败：理解错方向就动手

先说一个可能和你直觉相反的观察：

AI 最常见的失败，不是它不会做，而是它一开始就理解错了。

它很擅长执行。你说「把这堆资料整理成一份文档」，它能写得又快又整齐。但如果它理解成「整理成一份给老师看的报告」，而你其实要的是「给自己复习用的提纲」，那么它做得越认真，浪费越大。

更麻烦的是，它通常不会在没听懂的时候停下来问你。你给了一个模糊的指令，它会自己挑一个解释，然后往下做——因为「往下做」是它的默认行为。

后果是一个很常见的循环：

1. 你说了一件有点模糊的事。
2. 它按自己的理解做了十分钟。
3. 你一看，方向不对。
4. 你重新解释一遍。
5. 它重做一遍。

十分钟加十分钟，还有你重新解释的时间。这一整轮，只要它一开始问你三个问题就能避免。

### 7.4.2 把这句话记下来

这一节最重要的一句话，建议直接背下来：

先别动手。先问我最多 5 个问题，把我的需求问清楚，再给我方案，我确认后你再做。

这句话里有四个设计，每一个都有用：

| 这句话的部分 | 作用 |
|---|---|
| 先别动手 | 阻止它的默认行为——立刻开始做 |
| 最多 5 个问题 | 给上限。不设上限，它可能问十几个问题，变成审讯 |
| 先给我方案 | 让你在它动手之前看到它的理解。方案不对立刻纠正，成本最低 |
| 我确认后你再做 | 留出一个关口，中间有一次你的检查机会 |

特别说一下「最多 5 个」为什么必要。 不设上限会走向两个极端：一种是它什么都不问直接干；另一种是它一口气问十二个问题，你答完已经累了，而且其中一半你自己也没想清楚。

五个是个合适的量。足够覆盖关键的不确定处，又不至于让你疲劳。

### 7.4.3 三个场景的变体

做文档、写东西的时候：

先别动手。先问我四个问题：这份东西给谁看、大概多长、要什么格式、

必须包含哪几点。问完给我一个提纲，我确认后你再写。

关键在于把要问什么直接列出来。你不列，它可能问你「要不要加插图」这种不重要的问题，而漏掉「给谁看」这个决定一切的问题。

要改文件、动数据的时候：

先别动手。先告诉我你打算改哪些文件、每个文件改什么、改完之后会变成什么样。

我同意之后你再改。

针对的是「有影响的操作」。改文件不像写文档，写错了删掉重来就行——改文件可能覆盖掉你原来的内容。先看计划再批准，是这里唯一安全的做法。

查资料、做调研的时候：

先把我问的问题复述一遍，确认你理解对了，再开始查。

针对的是「理解偏差」。查资料最怕它查了一个相近但不是你要的问题，回来给你一堆看着相关其实没用的东西。让它先复述，一句话就能发现偏没偏。

### 7.4.4 怎么判断它问得好不好

它问完问题之后，你可以用问题的质量判断它理解得怎么样。

- 问得具体 → 它理解了任务，正在确认细节。比如「这份提纲是给考试复习用，还是给课堂展示用？」
- 问得笼统 → 它没抓住重点。比如「你想要什么样的效果？」
- 问得离谱 → 大概率是你的描述有问题。它从你的话里只能推出这个理解，说明你的话有歧义。这时候不要怪它，回去改你的描述。

最后一条尤其值得记住：它问出的怪问题，是你能拿到的最好的反馈。 它直接告诉你你的描述在哪个地方可以被误读。

还有一步经常被跳过：它问完、你答完，要让它再复述一遍任务。 复述对了，才算真的理解——它可能把你的回答理解错了，也可能漏掉其中一条，而这时候纠正的成本最低。可复制的句式见 7.6 节的方法十一。

## 7.5 一段完整的描述，有四个部分

它会追问，但这不能替你省掉一件事：你自己得说清楚。

一条实用经验：描述清楚比换一个更强的模型划算得多。 换强模型，是在它理解偏差的基础上做得更快；把话说清楚，是让偏差根本不发生。后者的收益大得多，而且不额外花钱。

一段完整的描述有四个部分：

1. 目标——你要做成什么。
2. 验收标准——做成什么样算成功。
3. 边界——不要做什么。
4. 失败处理——做不成怎么办。

第 3 部分最容易被漏掉，但它往往最有用。「不要用专业术语」「不要超过一页」「不要改我原来的标点」——这些否定式的约束，恰恰最能防止它跑偏。

下面是同一件事的两种说法。左边是常见说法，右边是说清楚之后的样子。

| 说得含糊 | 说得清楚 |
|---|---|
| 帮我写个介绍 | 写一段 300 字的介绍，给大一新生看，分三段，不要堆形容词，结尾给一句具体建议 |
| 这个方案怎么样 | 按事实、逻辑、完整度三项各打分，指出最致命的三个问题，每个问题给一条改法 |
| 帮我看看这个文件 | 读一下 资料.md，列出里面出现的所有人名和他们对应的事件，做成表格 |
| 优化一下 | 把超过 30 个字的句子拆短，删掉所有「进行」「相关」「方面」这类虚词，意思不要改 |
| 帮我整理一下 | 按时间顺序重排，同一时间的合并成一条，每条不超过两行，标上信息来源 |
| 写详细点 | 现在 800 字，扩到 2000 字，补充具体例子，不要靠加形容词来凑字数 |
| 这个能用吗 | 检查有没有事实错误和前后矛盾，逐条列出你发现的问题；没发现就说明你检查了哪些方面 |
| 再改改 | 上一版我说了三个问题，逐个确认改掉了没有；改掉的说明改在哪，没改的说明为什么 |

看右边那一列的共同点：都有具体的数量、格式或动作。 它们不描述「想要什么感觉」，只描述「要做到什么程度」。

「说清楚」不是要把话说长，而是要把话说到能验收。 上面右边那些句子都不长。

还有一个附带好处：你为了说清楚而想的过程，本身就会让你发现自己也没想明白的地方。写不清楚，往往是因为还没想清楚。

## 7.6 十三个把提示词写好的方法

上面讲的是原则，这一节讲具体手法。每个方法都写了「什么时候用」和一个例子，按你实际会遇到的场景挑着用。

### 7.6.1 方法一：给它一个例子

什么时候用： 你要的格式或风格很难用话描述清楚，但你能认出来。

做法： 给一个「好」的例子，再给一个「不好」的例子。它照着对照，一次就准。

```text
按这个格式写，不要按第二个：
【好】
- 问题：数据没有来源
- 位置：第三段
- 改法：补上引用，或改成推测语气
【不好】
- 第三部分论证不够充分，建议加强。（没有指明位置和具体改法）
按【好】的格式，处理下面这份评语：
（粘贴内容）
```

为什么要给反例： 只给正例，它可能抓不到边界，给你一个「像但不对」的结果。给了反例，它就知道该避开什么。

### 7.6.2 方法二：先要大纲，再要正文

什么时候用： 要写的东西比较长，或者结构比措辞更重要。

做法： 分两步。先只要提纲，你确认或修改之后，再让它展开。

```text
第一步：先给我一份提纲，只列各级标题和每部分要点，不要展开。
等我确认之后再写正文。
```

好处： 结构错了改提纲是一分钟的事；结构错了改两千字的正文是半小时的事。

### 7.6.3 方法三：指定输出格式

什么时候用： 结果你要拿去用、要贴到别处、或者要跟别的东西对齐。

做法： 把格式说死——表格还是列表、有哪几列、每列叫什么、字数上限。

```text
用表格输出，四列：编号、位置、问题、改法。
每个问题一行，改法不超过 30 字。不要写表头之外的说明文字。
```

一个常见坑： 不说「不要写表头之外的说明文字」，它会在表格前后各加一段解释。凡是你要直接拿去用的输出，都要加一句「不要额外的说明」。

### 7.6.4 方法四：明确「不要什么」

什么时候用： 它犯的错是「多做了」而不是「少做了」——加了没用的内容、用了你不喜欢的词、擅自改了你的东西。

做法： 把不要的东西列出来。这一条比「要什么」更容易执行，因为边界更清楚。

```text
不要：不要加总结段，不要用「综上所述」，不要改我原文的标点，
不要把专业名词换成通俗说法，不要在结尾问我还有没有别的需要。
```

为什么有效： 你是在减掉它的默认行为。它的默认行为包括加总结、加客套、加追问，这些多数时候是多余的。

### 7.6.5 方法五：拆阶段，一次只做一件事

什么时候用： 任务有多步，而且你担心中间某一步做错。

做法： 明确说「这一步只做这一件事，做完停下来等我」。

```text
这一步只做一件事：把这个 PDF 里的题目提取出来。
不要开始整理格式，不要生成答案，不要写文件。做完把前 5 道题贴给我看。
```

好处： 每一段都有检查点。错误在最早的地方就被拦住，不会滚到后面。

### 7.6.6 方法六：让它标出不确定的地方

什么时候用： 涉及事实、数据、原文内容——任何它有可能编造的地方。

做法： 明确要求它区分「确定的」和「不确定的」。

```text
凡是你不确定的内容，标上 [不确定]，并说明你不确定的原因。
不要猜，也不要为了看起来完整而补全。
```

这一条极其重要。 它最大的风险不是做错，而是做错的时候看起来和做对一样正常。让它自己标出来，你才知道该核对哪里。

### 7.6.7 方法七：基于上一版提增量要求，不要重说一遍

什么时候用： 已经出过一版，你想改其中几处。

做法： 只说改什么，并明确「其他部分不要动」。

```text
在上一版基础上改三处：
1. 把第二段的结论提到开头。
2. 第三段的数据补上来源。
3. 删掉最后一段。
其他部分一律不要动，包括标点。
```

为什么不要重说一遍： 重说一遍等于让它重新生成，上一版你满意的部分可能被改掉。增量修改比重做安全。

### 7.6.8 方法八：要它给多个方案，你再选

什么时候用： 你自己也不确定想要哪种，但看到选项能判断。

做法： 要三个差异明显的方案，只要思路不要展开。

```text
给我三个不同的方案，它们的思路要明显不同。每个方案只写：
核心思路（一句话）+ 优点 + 缺点。不要展开细节。
我选一个之后你再细化。
```

关键在「明显不同」这四个字。 不说这句，你会拿到三个几乎一样的方案——它倾向于收敛到同一个答案。

### 7.6.9 方法九：让它解释理由

什么时候用： 你要判断它的结论可不可信，或者要拿去跟别人解释。

做法： 要求它说明依据，并区分「有依据」和「推测」。

```text
给出结论之后，逐条说明每条结论的依据是什么。
依据来自我提供的材料 / 来自通用知识 / 是你的推测——这三种要标清楚。
```

最后那半句是关键。它把「通用知识」和「推测」混在一起说的时候，你无法判断该信多少。

### 7.6.10 方法十：补上语境

什么时候用： 默认情况下它会假设一个「一般读者」。但如果你的读者很具体，结果就会不对。

做法： 说清三件事——给谁看、什么场合、对方什么水平。

```text
这份东西是发给这些人的：大一新生，第一次接触这个主题，
只会用手机看，大概只会花三分钟。
```

同一份内容，给新生看和给老师看，应该是两份不同的东西。 你不说，它只能按平均值写，而平均值的读者并不存在。

### 7.6.11 方法十一：让它先复述，再执行

什么时候用： 前面已经聊了很多轮，或者任务比较复杂。

做法： 在它动手前加一道确认。

```text
先不要做。把你理解的任务复述一遍：我要什么、分几步、每步产出什么。
我确认后再开始。
```

它复述得越具体，说明理解得越深。 复述里出现「大概」「应该是」这类词的地方，就是它没把握的地方。

### 7.6.12 方法十二：提示词写不好，就让它帮你写

什么时候用： 你已经改了三遍还是不满意。

做法： 把问题反过来问——让它帮你改提示词。

```text
我下面这段话一直得不到想要的结果。请帮我改写成一段更清楚的指令：
指出我哪里描述得含糊，改写之后告诉我你补上了哪些信息。
我原来的话：
（粘贴你写的那段）
```

这是这一节里最省力的一个方法。 它知道自己的「理解方式」，所以它比任何人都清楚你那句话会在哪里被误读。

### 7.6.13 补充一条：让它写文件之前，先说一句「先看看有没有」

这一条来自一次真实的翻车，非常值得记住。

情况：你让 AI「把报告写到某个文件」。如果那个位置已经有一份文件，它很可能直接把原文件覆盖掉——而且不会提醒你。从它的角度看，「写入指定文件」就是它被要求做的事。

后果：原来的内容没了。如果那是上一轮 AI 的产出，或者你自己写的东西，就找不回来了。

做法：在写入类指令后面固定加一句：

```text
写之前先检查目标文件是否已存在。
如果已存在，先告诉我它有多少内容、开头是什么，等我确认后
再决定是覆盖、追加，还是换个文件名。
```

这一条在「让多个 AI 各写一份」的时候尤其重要。 你派了三个人各写一份评审报告，如果路径写重了，或者有一份被要求「写到同一个位置」，后写的就会把先写的顶掉——而你直到去收报告时才会发现少了一份。

一句可以直接背的话：凡是让 AI 写文件，都加一句「先看有没有，有就先告诉我」。

### 7.6.14 用哪几个

十三个不用都记。按这个顺序上手：

1. 先固定用方法六（标出不确定）。这一条能防止最坏的情况。
2. 再固定用方法四（明确不要什么）。这一条最省事，效果最直接。
3. 遇到长任务，加方法二和方法五（先大纲、拆阶段）。
4. 其他方法按需查。 想不起来的时候翻回 7.6 节开头。

## 7.7 什么时候问题不在提示词上

改了描述还是不理想，可能是另外三种情况。分清楚，能省下很多时间。

| 现象 | 真正的问题 | 该怎么办 |
|---|---|---|
| 换了三种说法，它都理解不到你要的点 | 任务本身没想清楚 | 停下来，先自己把要求写成一两句话。写不出来就别急着让它做 |
| 要求很清楚，但它就是做不好 | 模型能力不够 | 换 deepseek-v4-pro，或者把任务拆细 |
| 要求很清楚，它做得到，但结果你不满意 | 这是口味问题 | 别再改了，自己动手调整那几处，比来回对话快 |

第三种最容易被忽视。AI 做出来的东西「不够你的味道」，继续对话往往改不出来——你自己花五分钟调一下，比跟它来回十轮都快。

## 7.8 让 AI 帮你更新 AI

这一节讲这套方法里最有意思的部分：用 AI 来维护 AI 自己。

这类工具更新很快。你面对的问题不是「学不会」，而是「学的东西会过期」。三种做法可以应对。

### 7.8.1 做法一：让它读更新日志，回答「对我有什么影响」

不要这样问：

帮我总结一下这个更新日志。

你会得到一份摘要，说的是「发布了什么」。但你真正要知道的是另一件事。

要这样问：

这是 DSH 的更新日志。不要给我摘要。请回答三个问题：

一、哪些改动会影响到我现在的用法？

二、有哪些我一直在用的东西被改掉了，我需要做什么？

三、有没有新增的、对我有用的能力？

「对我有什么影响」和「发布了什么」，是两个完全不同的问题。 前者才是有用的那个。

### 7.8.2 做法二：让它修坏掉的东西

升级之后常见的后果是：某些技能不灵了、某些插件失效了、某些设置项变了。

```text
我刚刚升级了。请检查一下我 ~/.dsh/skills/ 下的技能，
哪些步骤可能已经和当前版本不符？先列出问题，不要直接改。
```

注意最后那句「先列出问题，不要直接改」——这是 7.4 节的用法。先看方案，再批准执行。

### 7.8.3 做法三：维护一份「环境档案」

这是本书给你的一个建议，也是我认为最值得做的一件事。

在你的工作区里建一个文件，专门记录你自己的这套环境：

```text
# 我的环境档案
## 版本记录
| 日期 | 版本 | 变化 |
|---|---|---|
| 2026-09-16 | 0.1.5-rc.1 | 初始安装 |
## 我装了哪些插件
| 名字 | 用途 | 装的时间 |
|---|---|---|
## 我改了哪些设置
| 改了什么 | 改成什么 | 为什么 |
|---|---|---|
| 默认模型 | deepseek-flash | 日常任务够用 |
## 我踩过的坑
| 日期 | 现象 | 原因 | 怎么解决的 |
|---|---|---|---|
## 我常用的几句话
（把 7.4 节那句追问指令、常用的描述模板存在这里）
```

为什么这个文件有价值：

- 它能回答「我上次是怎么解决的」——不用再搜一遍。
- 它能回答「我装过什么」——重装或换电脑时照着恢复。
- 它是跨会话的记忆。第 7.2 节说过，新会话它就什么都不知道了；但你可以说「看一下 `环境档案.md`」，它立刻就知道你的情况。

而且这个文件可以让它帮你维护：

看一下 `环境档案.md`，把这周的变化补进去。

这个文件就是「你的 DSH 和别人不一样」的地方。别人的教程给不了你这个。

## 7.9 两个例行仪式

上面三件事如果只是「想起来才做」，就不会做。给它们定个时间。

### 每周 15 分钟

选一个固定时间，做五件事：

1. 看版本。 有没有更新，有就更新。
2. 读变更。 让它按 7.8 节的方法回答「对我有什么影响」。
3. 跑自检。 让它检查一遍技能和插件是否正常。
4. 更新技能。 把坏掉的修掉，不用的删掉。
5. 记一条。 往环境档案里补一行。

为什么是每周： 大版本不会天天出，但小变化一周总有一点。每周一次刚好，既不频繁，也不会积累成一堆问题。

### 每月一次大扫除

半小时左右，做四件事：

1. 删不用的插件。 三个月没用的删掉。
2. 合并重复的技能。 两个技能做同一件事，留一个。
3. 归档旧会话。 重要的产出确认已存成文件，然后清理会话。
4. 看一次用量。 上个月花了多少，主要花在哪（第 7.3 节）。

大扫除的意义是防止拖累。 插件和技能都不是越多越好——装太多会让它变慢，也会让它更容易挑错工具。

## 7.10 信息源分级

关于这类工具的信息，质量差别极大。养成一个习惯：先判断来源，再决定信几分。

| 等级 | 来源 | 怎么对待 |
|---|---|---|
| 一手 | 官方文档、官方仓库的发布说明 | 可以当事实用 |
| 二手 | 社区市场、教程文章、视频 | 先对版本号，再决定试不试 |
| 传言 | 群聊截图、「据说」「我朋友说」 | 不要当事实用 |

一条规则：一手来源里没有的东西，不要当事实用。

这条规则会帮你省很多时间。群里有人说某个参数能用，你去官方文档里找不到，那就不要花半小时试它——很可能那个人用的是另一个版本，或者记错了。

还有一条：所有教程先对版本号。 看一篇文章，第一件事是找它的发布日期和适用的版本。没有这两个信息的教程，价值会大打折扣。

这本书是二手资料。 我用到的命令都标注了核对日期，你看到命令报错时，先对版本号，再看附录 E 的勘误页。

## 7.11 用 AI 学 AI 的正确姿势

最后讲怎么用它提升自己，而不是越来越依赖它。

四种有效的用法：

一、让它举反例。

「我说 AI 每次都会记得我说过的话，你举几个反例。」能举出反例，说明这个理解有问题——这是发现错误最快的方式。

二、让它指出你的错误理解。

「关于技能和插件的区别，我理解成 X，这个理解有没有问题？」直接问，比你自己猜快。

三、让它出题考你。

「根据我们刚才讲的内容，出五道题考我，先不要给答案。」然后自己答，再让它批改。这个方法对付考试有效，也适合检验自己是不是真看懂了。

四、让它讲到你懂为止。

「这个我没听懂，换一个说法再讲一遍，不要用行话。」听不懂就继续要求换说法——这是你付费买到的服务，不用不好意思。

一条底线：

能向别人讲清楚，才算学会。

这条标准很硬，但很准。你能用自己的话把一件事讲给同学听，并且他能听懂，说明你真的理解了。讲不出来，多半只是「看着眼熟」。

这也是本书第 1 章的验收全是口述题的原因。能说出来，比做过一遍更接近掌握。

## 本章验收

验收内容：完成一次完整的每周更新仪式。

具体做五件事，并把结果写进你的环境档案：

1. 查一次你的 DSH 版本，和本书前言里的版本锚点表对照，看有没有变化。
2. 让它读一次更新信息，回答「对我有什么影响」。这段时间没有更新，就让它检查一遍技能是否正常。
3. 检查 `~/.dsh/skills/` 下的技能，修掉或删掉有问题的。
4. 建好 `环境档案.md`，把今天的版本、装的东西、踩过的坑填进去。
5. 把 7.4 节那句追问指令，以及 7.6 节里你最常用的两个方法，存进档案的「常用的话」一节。

验收：一份你自己的 `环境档案.md`，里面有版本记录、已装清单、踩过的坑和常用指令。

做完这个验收，你已经有了不被落下的基础：不是记住所有细节，而是有一套发现自己该更新什么的方法。
