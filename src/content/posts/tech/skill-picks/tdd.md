TDD 常被误解成"多写点测试"。它真正的意思是反过来的：**用测试来决定你要写什么**——先把期望钉死，再让实现去满足它。

这是 Superpowers 里的 `test-driven-development` 技能，它把这件事变成了**没有商量余地的硬规矩**。

## 铁律

技能原文里就一句全大写：

```text
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

先写了代码怎么办？**删掉，从头来**。而且写得很细：不许留着"当参考"，不许"边写测试边改装它"，不许去看它。删就是删。

后面还有一句我觉得更狠的：**"违反规则的字面，就是违反规则的精神。"** 意思是别拿"这次特殊"给自己开后门。

## 红-绿-重构

循环是四步，中间有两个**验证点**：

1. **红**：写一个会失败的测试
2. **验证红**：跑起来，**亲眼看它按预期失败**（不是"报错了就行"）
3. **绿**：写刚好能让它通过的最小实现
4. **验证绿**：跑起来看它通过，全绿之后才重构；重构过程中要保持一直绿

为什么非要"看着它失败"？原文那句解释很到位：

> 如果你没看着测试失败，你就不知道它到底测了什么。

一个从来没红过的测试，很可能压根没测到你以为的那件事。

## 什么时候必须用，什么时候可以商量

| 情况 | 态度 |
| --- | --- |
| 新功能、修 bug、重构、行为变更 | **必须**——没有例外 |
| 一次性原型、生成的代码、配置文件 | 可以例外，但技能要求**先问过你** |
| 你心里想"这次就先跳过吧" | 原文：停。那是自我合理化 |

## 和 Superpowers 的关系

它不是一个孤立的技能，而是 Superpowers 流程里的第 5 环：

```text
brainstorming（想清楚）→ writing-plans（拆开）→ TDD（实现）→ requesting-code-review（审查）
```

单独装也能用，但配起来才完整——计划里的每个任务本来就被要求写清"怎么验证"，TDD 正好接在那一句上。

## 什么时候别用

- **老项目没有测试基础时别硬上**。先给关键路径补少量测试，再谈驱动开发
- **UI、交互、样式类的改动成本很高**。写起来费劲、维护更费劲，这类更适合人工验证 + 少量关键断言
- **别为了流程而流程**。它的价值在于"想清楚再写"，如果你的需求本来就只有一种实现方式，写测试只是多一道手续
- 它管的是实现环节。**需求本身是错的，测试写得再好也只是把错的东西固化下来**
